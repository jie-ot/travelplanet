# 🪐《旅行星球》外部事实源与工具调用规范

> **⚠️ 给 coding agent 的核心系统指令**：
> **本文主定义**：外部事实源、MCP、Function Calling、RAG 的使用边界；Provider 白名单与接入方式；工具内部 Schema（`TravelFactPack`、`BookingEvidence` 等）；配置项；失败降级状态与模型措辞约束；工具日志脱敏；禁止事项。
> **本文不主定义**：`tool_call_logs` 表结构（《数据库表结构与迁移规范》十二）；调用时序与业务落点（《任务详细流程规范》十四）；模型调用协议（《后端与大模型通信接口规范》）；前后端 DTO（《数据结构与通信接口规范》——**工具能力的引入严禁改变任何前后端接口字段**）。

## 一、定位与总原则

1. 本项目允许在 Demo 阶段适度、有边界、可控地使用外部事实源，以增强预订指南、交通、距离、天气、景点开放等旅行事实的可信度；但本项目是"受控工具"模式，**不是**开放式联网 Agent。
2. 任何工具必须同时满足六个条件才允许接入：白名单内、输入/输出 Schema 化（Pydantic）、配置化（Key/URL/开关/超时/重试均经 `config.py`）、可审计（写 `tool_call_logs`）、可降级（失败有明确降级状态）、日志脱敏。六条任缺其一，严禁接入。
3. 决策权归属：后端固定工具白名单、参数 Schema、轮次上限与实际执行权；模型可通过 Function Calling 在该白名单中提出调用，`orchestrator` 拦截后由 `travel_fact_service.execute_tool()` 决定执行或降级。endpoint、前端和模型都不能接入白名单外工具，模型不能自由联网或搜索。
4. 工具结果与模型输出同样不可信：必须先经 Pydantic 校验，再注入 Prompt 或参与业务判断。
5. 工具失败不单独导致业务接口失败：事实包构造异常被 `planning_service` 捕获后以无事实包继续，单次 Function Calling 异常由执行器转为结构化错误或 B 类指引。若工具代码异常逃逸到应用全局处理器，才会按普通未处理异常映射 `1003`。
6. **优先-降级总则（火车票/机票专用）**：火车票、机票优先尝试 A′ 类社区 MCP 获取参考事实；只要 A′ 未启用、未配置、超时、报错或返回空，**必须自动、静默降级为对应 B 类入口指引**（状态 `needs_official_confirmation`），严禁因 A′ 不可用而让接口失败或让模型脑补。A′ 是"锦上添花"，B 是"永远兜底"。

## 二、能力分类

白名单 Provider 分三类，coding agent 只能在三类已列 Provider 中选择，严禁新增类别或 Provider：

1. **A 类：官方可联网事实型 Provider**——拥有官方授权开放 API，合规、稳定、可用于正式演示。当前代码已接入高德 REST（`amap`）的城市天气、关键词 POI、周边 POI、地理编码辅助路线、驾车/步行/骑行/公交路线；高德 MCP、详情/距离/IP 定位与和风天气（`qweather`）属于白名单预留能力，按需补齐。这是模型获取"可信真实事实"的首选来源。
2. **A′ 类：社区 MCP 事实型 Provider（参考级，研究/演示用）**——当前有 12306 社区 MCP（`rail_query_mcp`）与机票社区 MCP（`flight_query_mcp`）。火车开关默认开启，机票开关默认关闭；只有 `TOOLS_ENABLED`、对应开关和 stdio endpoint 都有效时才调用。未启用、预热中、超时、报错或空结果都返回对应 B 类入口指引；成功结果仍必须附“以官方实时为准”。
3. **B 类：入口指引型 Provider（不联网，永久兜底）**——12306、携程旅行、美团、酒店平台等场景的**确定性官方入口指引**：后端用本地规则/模板生成"去哪个官方渠道、查什么、注意什么"的结构化指引，状态恒为 `needs_official_confirmation`，不发起任何网络请求。B 类既是 A′ 失败时的兜底，也是酒店/本地生活等无 A′ 路径场景的唯一形态。

### 三·补充：A′ 类接入细则（固定仓库、固定协议、固定命令）

- 当前只支持 `stdio:` endpoint。`mcp_stdio.py` 在独立事件循环线程中维护持久会话，对上层提供同步调用；冷启动在后台进行，请求线程在会话尚未就绪时立即得到空结果并降级，不会为冷启动等待完整启动超时。

**(1)** `rail_query_mcp` ****

- 火车票场景当前 Demo 默认使用实测可用的 Node 版 `12306-mcp`

- 协议与启动：
  - stdio：`RAIL_MCP_ENDPOINT` 配为命令 stdio:npx -y 12306-mcp ；
- 默认 Node 包适配先调用 `get-station-code-of-citys`，再调用 `get-tickets`；兼容旧 endpoint 名称时也支持 `search-stations` + `query-tickets`。返回最多筛选 16 个候选并整理为 `RailFact`；不调用换乘、经停或独立票价工具。

**(2) `flight_query_mcp` —— `github.com/xiaonieli7/FlightTicketMCP`**

- 当前只调用 `searchFlightRoutes`，参数为 `departure_city`、`destination_city`、`departure_date`，取返回列表第一条整理为 `FlightFact`。不调用中转、航班跟踪、详情或天气工具。默认关闭该 Provider，Function Calling 会直接得到 B 类机票入口指引。

**(3) 版本与稳定性**：建议在 `requirements`/部署脚本中锁定具体版本（如 `mcp-server-12306==x.y.z`、`flight-ticket-mcp-server==1.0.x`），避免上游变更导致 Schema 漂移；适配器必须容忍工具不存在/字段缺失/返回结构变化，任一异常即触发 B 类降级，严禁让异常冒泡。

## 四、工具内部 Schema（放在 `app/ai/tools/schemas.py` 或 `app/ai/schemas.py`）

工具 Schema 属于模型内部结构，严禁替代或污染前后端 DTO。必须至少定义以下结构（字段可按实现微调，但状态枚举与分层不得改变）：

```python
from pydantic import BaseModel
from typing import Literal

FactStatus = Literal["ok", "unknown", "timeout", "provider_not_connected", "needs_official_confirmation"]

class ToolCallResult(BaseModel):
    tool_name: str
    provider: str                      # amap / qweather / rail_query_mcp / flight_query_mcp / entry_guide
    status: FactStatus
    degraded_to_b: bool = False        # A′ 失败已降级为对应 B 类入口指引时置 true
    latency_ms: int | None = None
    error_code: str | None = None

class RouteFact(BaseModel):            # amap_route
    origin: str
    destination: str
    mode: Literal["driving", "transit", "walking", "bicycling"]
    distance_km: float | None
    duration_minutes: int | None
    status: FactStatus

class WeatherFact(BaseModel):          # amap_weather / qweather_forecast
    city: str
    date: str                          # YYYY-MM-DD
    summary: str | None                # 如 "多云 18-26℃"
    status: FactStatus

class PoiFact(BaseModel):              # amap_poi_search / amap_geocode
    name: str
    address: str | None
    location: str | None               # "lng,lat"
    category: str | None
    status: FactStatus

class BookingEvidence(BaseModel):      # B 类入口指引 + A 类位置事实的预订证据
    booking_type: str                  # 如 "火车票"、"机票"、"酒店"、"景区门票"
    official_channel: str              # 如 "12306 官方 App/网站"、"丽江文旅微信小程序"
    query_hint: str                    # 建议查询条件，如 "2026-07-10 大理→丽江 动车"
    notes: str | None                  # 通用注意事项（候补、提前预约等），不含编造实时数据
    status: FactStatus                 # B 类恒为 needs_official_confirmation

class RailFact(BaseModel):             # A′ rail_query_mcp（参考级，非权威）
    origin: str
    destination: str
    date: str                          # YYYY-MM-DD
    train_no: str | None               # 车次，如 "G1234"
    depart_time: str | None            # "08:30"
    arrive_time: str | None            # "12:05"
    duration: str | None = None         # 历时，如 "05:53"
    seat_class: str | None             # 席别，如 "二等座"
    ref_price: float | None            # 参考票价，非实时、非可订
    source: str = "community_mcp"      # 数据来源标识，固定社区 MCP
    status: FactStatus                 # ok 时仍为"参考级"，模型须附"以官方为准"

class FlightFact(BaseModel):           # A′ flight_query_mcp（参考级，非权威）
    origin: str
    destination: str
    date: str                          # YYYY-MM-DD
    flight_no: str | None              # 航班号，如 "MU5100"
    depart_time: str | None
    arrive_time: str | None
    aircraft: str | None               # 机型
    ref_price: float | None            # 参考票价区间下限，非实时、非可订
    source: str = "community_mcp"
    status: FactStatus

class TravelFactPack(BaseModel):       # 注入 Prompt 的唯一事实容器
    request_id: str
    generated_at: str                  # ISO 8601
    routes: list[RouteFact] = []
    weather: list[WeatherFact] = []
    pois: list[PoiFact] = []
    rails: list[RailFact] = []         # A′ 火车票参考事实（可空，降级时为空）
    flights: list[FlightFact] = []     # A′ 机票参考事实（可空，降级时为空）
    booking_evidences: list[BookingEvidence] = []
    tool_calls: list[ToolCallResult] = []
```

规则：1. 首轮不预注入 B 类 `TravelFactPack`；Function Calling 结果作为 `role=tool` 的紧凑 JSON 回填，原始 HTTP/MCP 响应不直接给模型。2. 每条可选择事实附请求级 `fact_id`；模型每轮通过 `update_planning_fact_state` 选择后续可能使用的 ID，后端解析回完整原始字段并裁剪未选事实的上下文副本，原始 Provider 结果不由后端做语义取舍。3. 高德失败结果保留 `provider_not_connected/unknown` 状态与确认提示；A′ 失败不生成空 `RailFact/FlightFact`，而是直接返回 `needs_official_confirmation` 的 B 类指引。4. A′ 成功结果仍带 `reference=true`、免责声明和 `official_entry`。5. 系统提示提供通用 B 类官方入口规则，模型只能在相关 A/A′ 工具失败、未连接或不适用时使用。

## 五、调用链路与代码落点

1. 唯一链路：`planning_service.py`（或未来明确批准的业务 Service）不做首轮 B 类预注入 → 模型在受限 Function Calling 中提出必要工具调用 → `travel_fact_service.execute_tool(...)` 按白名单、配置与输入 Schema 执行 A/A′ 工具并回填结果。`needs_facts(...)` 当前恒为 false；兼容保留的 `build_fact_pack(...)` 只返回空包且不得调用高德、12306 MCP 或机票 MCP。
2. 所有 A 类高德事实与 A′ 火车/机票参考事实必须由 Function Calling 工具返回后才能写入行程。系统提示中的 B 类官方入口只用于相关 A/A′ 查询失败、未连接或不适用后的兜底，不代表已经完成查询。
3. **A′ 优先-降级算法（火车票/机票，仅 Function Calling 执行时适用）**：对每次 `query_rail_tickets` / `query_flights`，按以下确定性顺序处理，禁止跳步：
  ```
   若对应 A′ 开关关闭或总开关关闭：
       直接生成 B 类 BookingEvidence(needs_official_confirmation)；日志 degraded_to_b=false
   否则调用 rail_query_mcp / flight_query_mcp
       （火车单次受 TOOL_TIMEOUT_SECONDS 约束，机票受 FLIGHT_MCP_TIMEOUT_SECONDS 约束；MCP 层当前不按 TOOL_MAX_RETRY 重试）
       若成功且有有效结果：
           返回 RailFact / FlightFact（status=ok，source=community_mcp）
           同时返回同行程的 B 类 BookingEvidence 作为 official_entry
       若 endpoint 未配置 / 预热中 / 超时 / 异常 / 空结果：
           返回 B 类 BookingEvidence(needs_official_confirmation)；日志 degraded_to_b=true
  ```
   要点：A′ 成功时 A′ 参考事实与 B 类官方入口"并存"（参考 + 确认双轨）；A′ 失败时静默退回纯 B；无论哪种结果，Function Calling 返回中**永远至少有一条 B 类入口指引兜底**，确保模型有可信的"官方确认"话术。
4. 严禁：endpoint 直接调用工具；预取阶段调用 A/A′；Prompt 模板内写死非白名单工具调用；模型通过自由文本"要求"后端去访问某网站；任何组件绕过 `travel_fact_service.py` 直接 import Provider 适配器；A′ 异常向业务层冒泡。
5. 当前规划使用受限 vivo Function Calling：模型发出的外部 function call 由 `orchestrator.py` 拦截、经 `travel_fact_service.execute_tool(...)` 校验参数并执行；最多 5 个**实际执行的外部工具批次**、总计最多 75 次外部调用，内部 `update_planning_fact_state`、缺失/无效 FactState 的协议纠正响应均不占这 5 轮。模型应在一次正常响应中同时更新 FactState 和提出下一批外部调用；更新后只将完整已选事实、新一批尚待筛选结果和 `missing_facts` 带入下一轮。同响应已安排查询的项目不再列为缺失，失败时下一轮补回；最后一个批次集中处理剩余缺失项。达到上限后追加无工具最终回答，并将未解决项降级为 B 类确认提示，禁止生成精确事实。另设独立模型交互安全上限防止协议异常无限循环。最终 JSON 解析失败时先进行一次保留工具能力与历史的定向修复，必要时执行新增工具调用并无工具收口；仍失败才进行一次保留工具历史的无工具完整重生成。两类补救请求均为单次 HTTP 尝试，超时分别为 60 秒和 90 秒。
6. Function Calling 回填给模型的单次返回上限：`amap_weather` 1 条；`amap_route` 1 条方案；`amap_poi_search` 最多 20 条 `pois`；`amap_poi_around` 最多 20 条 `pois`；`query_rail_tickets` 最多 16 条 `candidates`；`query_flights` 保持现有参考结果或 B 类降级。
   当前参数校验只要求城市、日期、起终点、关键词等字符串非空，并未用正则验证 `YYYY-MM-DD`；周边半径必须大于 0，超过 50000 米时截为 50000。高德天气会优先匹配请求日期，未匹配时当前适配器回退到 Provider 返回的第一天预报，但 `WeatherFact.date` 仍保留请求日期。
7. `amap_route` / `amap_poi_around` 的地理解析规则：参数为 `lng,lat` 时必须坐标直通，不得再调用 geocode；模型应优先复用 POI 返回的 `location`。若路线参数是酒店/餐厅等商业 POI 名，或火车站、机场、客运中心、码头等交通枢纽名，后端优先调用 POI 文本搜索取坐标，再调用路线接口；普通地址仍优先 geocode，失败后才以 POI 搜索兜底。
8. RAG：当前阶段不引入向量数据库与检索管线；如未来需要，必须先修订本文，Demo 阶段视为禁止。
9. 每次 Function Calling 工具调用都尽力写入脱敏 `tool_call_logs`；写日志失败只记应用错误日志。仅在 A′ 开关打开且尝试后未得到结果时记录 `degraded_to_b=true`，显式关闭时为 `false`。

## 七、失败降级与模型措辞约束（主定义）

状态到模型措辞的映射写入 `context_builder.py` 与规划 Prompt。当前 `itinerary_validation_service.py` 只校验结构、日期与时间顺序，不对正文做航班号/价格拦截或清洗：


| 事实状态                                             | 模型允许的表达                                              | 模型禁止的表达                   |
| ------------------------------------------------ | ---------------------------------------------------- | ------------------------- |
| `ok`（A 类，真实）                                     | 可写成事实，如"驾车约 180 公里、2.5 小时（高德路线数据）"                   | 超出事实包字段的细节                |
| `ok`（A′ 类，参考级 `rails`/`flights`）                 | 可给出参考车次/航班与时刻，但**必须显式附"以 12306/航司官方实时为准，票价余票请官方确认"** | 把参考票价/余票写成确定可订结论；不附官方确认提示 |
| `needs_official_confirmation`（B 类恒定 / A′ 已降级）    | "建议在 12306 官方 App 查询 7 月 10 日大理→丽江车次并尽早购票/候补"        | 具体车次、票价、余票、房态、当天政策        |
| `unknown` / `timeout` / `provider_not_connected` | "建议以官方渠道/购票平台实际查询为准"                                 | 任何确定性实时结论                 |


通用红线（与《数据结构与通信接口规范》3.6 约束 5 一致）：无论工具状态如何，模型严禁编造具体航班号、实时票价、余票、酒店实时可订状态、景区当天政策、天气预报；事实包未覆盖的实时信息一律写"建议官方确认"。

## 八、日志与审计

1. 每次工具调用必须尽力写 `tool_call_logs`：`request_id`、`task_type`、`tool_name`、`provider`、脱敏输入/输出摘要、`status`、`latency_ms`、`error_code`。日志写入失败只能记录后端错误日志，不能影响 `/api/ai/planning`。
2. 脱敏铁律：严禁记录 API Key、access token、完整外部响应中的无关敏感字段、用户隐性特质全文、完整 Prompt；输入摘要只记录查询要素（如城市、日期、起终点），输出摘要只记录事实状态与关键字段。
3. 超时与重试：A 类工具超时 `TOOL_TIMEOUT_SECONDS`，重试最多 `TOOL_MAX_RETRY` 次且仅限网络类临时错误；参数错误、鉴权错误严禁重试，直接降级并记日志。

## 九、错误映射

工具失败默认不产生错误码：首轮以 `fact_pack=None` 开始；白名单外工具、参数校验失败、Provider 异常都以紧凑错误 JSON 回填模型。只有异常逃逸出规划流程并进入全局异常处理器时才返回 `1003`；Provider 原始错误不透传前端。

## 十、禁止事项清单

1. 严禁接入白名单之外的任何平台、网站、MCP Server、搜索引擎；2. **严禁本项目自身直接爬取或模拟登录 12306、携程、美团、飞猪、航司等任何平台页面**；火车票/机票的参考事实只能经白名单内 A′ 社区 MCP Server 间接获取，且必须遵守"研究演示、非商用、非生产、低频请求、可随时降级"的约束；3. 严禁让模型自由联网、自由搜索或自行"决定"接入工具；4. 严禁把第三方临时页面内容当可靠事实注入 Prompt；5. 严禁把用户隐性特质全文、用户照片、完整 Prompt 发给任何外部工具或 MCP；6. 严禁因工具实现修改前后端 DTO、接口字段、错误码、响应结构；7. 严禁绕过 `travel_fact_service.py`、绕过 Pydantic Schema、绕过 `tool_call_logs`、绕过 A′→B 降级算法；8. 严禁把 `status != "ok"` 的事实、或任何 A′ 参考事实写成确定可订结论；9. **严禁在 A′ 不可用时让接口报错或让模型脑补车次/航班**——必须静默降级到 B 类入口指引；10. 严禁在 migration、业务表或前端响应中出现工具侧原始 URL 或临时数据。

## 十一、实现验收清单

当前实现复核项：首轮不注入 B 类事实包，`build_fact_pack` 仅兼容返回空包；Function Calling 暴露六个外部工具和一个内部 FactState 工具；高德走 REST 且由总开关+Key 控制；高德 MCP、和风及高德详情/距离/IP 定位明确保持未实现；火车/机票 MCP 通过持久 stdio 会话适配，未启用或失败时返回 B 类指引；每个工具返回都经过 Pydantic/受控摘要边界；每次外部调用尽力写脱敏 `tool_call_logs`；工具故障不会单独使规划接口失败；工具能力不改变前后端 DTO。
