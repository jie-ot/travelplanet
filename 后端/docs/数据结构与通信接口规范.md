## 零、全局规范说明

### 0.1 基础 URL 与资源路径

> 后端落盘、FileAsset 生命周期、CORS 等基础设施铁律主定义见《后端技术栈与全局规范》一、二、三；本节只定义前后端通信如何拼 API、如何传资源路径。

- **前端环境变量**：前端（Next.js）配置 `NEXT_PUBLIC_API_BASE_URL` 与 `NEXT_PUBLIC_ASSET_BASE_URL`。Demo/内网示例：`NEXT_PUBLIC_API_BASE_URL=http://<实际内网IP>:8000/api`，`NEXT_PUBLIC_ASSET_BASE_URL=http://<实际内网IP>:8000`；正式部署推荐 `NEXT_PUBLIC_API_BASE_URL=/api`、`NEXT_PUBLIC_ASSET_BASE_URL=`（空串同源）。前端业务代码严禁写死 `localhost`、`127.0.0.1` 或具体 IP。
- **API 拼接规则**：所有 fetch/axios 必须经统一 `apiClient` 读取 `NEXT_PUBLIC_API_BASE_URL` 动态拼接，如 `${process.env.NEXT_PUBLIC_API_BASE_URL}/postcard-groups`；业务组件不再重复拼 `/api` 前缀。
- **只传相对路径**：Request/Response 严格只传以 `/static/` 开头的相对路径；前端严禁把拼接后的绝对地址传回后端，后端严禁返回完整资源 URL。完整地址拼接只发生在"前端渲染图片"边界：统一通过资源路径工具函数 `${process.env.NEXT_PUBLIC_ASSET_BASE_URL || ""} + 相对路径`，严禁在业务组件中直接拼域名。

### 0.2 鉴权机制

> 完整规则（`user_id` 预留、`get_current_user_id()`、数据隔离、JWT 升级路径）主定义见《后端技术栈与全局规范》四。前端相关仅两点：当前 Demo 免登录，所有请求 Header 不携带任何 Token/Session；前端对 `user_id` 完全无感知，不在请求体或 Header 中传递。

### 0.3 数据交互格式

| 场景 | Content-Type | 技术实现要求 |
|------|-------------|---------------|
| 所有 JSON 接口 | `application/json; charset=utf-8` | 后端必须用 Pydantic BaseModel 接收 Body，自动校验与反序列化。 |
| 文件上传接口 | `multipart/form-data` | 前端提交 FormData 时**严禁手动指定 Content-Type**，必须由浏览器自动生成带 boundary 的请求头；后端必须用 `UploadFile` + `File(...)` 接收。 |

### 0.4 流式传输

当前版本所有前后端接口均一次性返回（非流式）。AI 生成与规划对话均为请求-响应模式，前端展示 Loading 等待完整 JSON；后端是否使用工具/事实源不改变接口形态；流式、轮询、后台任务等机制当前禁止引入（并发与同步模型见《后端技术栈与全局规范》八）。

### 0.5 标准响应体结构（主定义）

> 设计理由：统一 `code/message/data` 三层包装，前端 `http-client.ts` 做一层通用解包。

注意：1. DELETE 或无特定返回数据时，`data` 显式返回 `null`；2. `RequestValidationError` 返回 HTTP 200 + `{code: 1002, message, data: null}`，而不是框架默认 422；3. **HTTP 状态码策略**：当前 FastAPI 应用把业务异常和进入全局 `Exception` 处理器的未预期异常都包装为 HTTP 200，由 `code` 承载状态；只有未进入应用处理器的协议/网关/进程级失败才可能出现裸 4xx/5xx。

```json
{ "code": 0, "message": "success", "data": {} }
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | `number` | 业务状态码：`0` 成功，非 `0` 失败（见 0.6） |
| `message` | `string` | 成功为 `"success"`，失败为人类可读错误描述 |
| `data` | `any` | 业务数据；空数据返回 `[]` 或 `null`（视接口而定） |

### 0.6 错误码定义（项目唯一错误码表，主定义）

| code | HTTP | 含义 | 前端行为 |
|------|------|------|---------|
| `0` | `200` | 成功 | 正常渲染 |
| `1001` | `200` | AI 生成失败 | 提示"生成失败，请重试"，允许再次触发 |
| `1002` | `200` | 参数校验失败 | 展示具体字段错误提示 |
| `1003` | `200` | 服务内部错误 | 提示"服务异常，请稍后再试"，不暴露内部细节 |
| `1004` | `200` | 资源不存在 | 提示"内容已被删除"，从列表移除该项 |

> 模型侧错误到本表的映射主定义见《后端与大模型通信接口规范》十；工具侧降级策略见《外部事实源与工具调用规范》七、九；严禁原样透传 vivo 网关错误，严禁新增错误码。

### 0.7 空数据约定

新用户（无任何历史数据）时，列表类接口返回 `{ "code": 0, "message": "success", "data": [] }`。

## 一、核心实体字典

> **重要**：前后端必须严格按以下 TypeScript 接口序列化/反序列化；后端 Pydantic BaseModel 字段名、类型、可选性必须完全对齐。

> **命名约定（务必贯彻）**：对外 DTO 实体（`PostcardGroup`、`Postcard`、`Report`、`Plan`、`FileAsset`、`UploadedPhoto`、`ReportChartPoint` 等）统一 **camelCase**；`ItineraryData` 一支（含 `trip_info`/`TripInfo`/`Preparation`/`Booking`/`DailyItinerary`/`Schedule`）统一 **snake_case**（对模型更自然、结构化输出更稳）。后端 Python/SQLModel/Service 内部字段一律使用 snake_case；对外 DTO 用 Pydantic v2 `alias_generator=to_camel` + `validate_by_name=True` + `validate_by_alias=True` + `serialize_by_alias=True` 输出 camelCase；`ItineraryData` 一支单独保持 snake_case、不参与 camel 别名转换。严禁同一层内混用两种命名。

### 1.1 明信片组 (PostcardGroup)

> 一次 AI 生成任务可能产出多张明信片（如 3 张），在"查看明信片"页以一个泡泡框聚合展示，封面为第一张；`PostcardGroup` 即该聚合容器。

```typescript
interface PostcardGroup {
  id: string                    // 唯一标识，后端生成（如 "pg_001"）
  location: string              // 旅行地点，城市级别（如 "大理"、"杭州"）
  startDate: string | null      // 旅行开始日期，ISO 格式；只能识别到月份则传 null
  endDate: string | null        // 旅行结束日期，ISO 格式；只能识别到月份则传 null
  dateLabel: string             // 展示用日期文案（如 "2025.06"、"2025.7.9-2025.7.12"）
  coverImage: string            // 封面相对路径 = 第一张明信片的 imageUrl
  postcards: Postcard[]         // 本次生成的全部明信片（通常 3 张，最少 1 张）
}
```

### 1.9 结构化行程数据 (ItineraryData)

- 设计理由：Pydantic 强制校验字段结构、类型、枚举与数值范围；模型内容仍需业务规则校验（日期连续性、每日行程数量、时间顺序、路径合法性等）。
- **当前稳定 ID 对齐**：`DailyItinerary.id` 与 `Schedule.id` 是编辑锚点。Pydantic 要求两个字段都存在且为字符串；Service 不补“缺失字段”，只会替换空值、前缀不是 `day_`/`sch_` 的值或同一天内已被占用的 schedule ID。有旧 context 时，day 先按有效旧 ID、再按日期匹配；schedule 先按 `(time_period, activity)` 精确匹配、再按剩余旧项位置复用。无法匹配的新项若模型已给未被同日其他条目占用的合法前缀 ID 则保留，否则由后端生成。该算法保证常规未改项稳定，但不是通用语义 diff。
- ID 生成策略：数据库业务 ID 与 schedule ID 使用业务前缀 + 12 位 UUID hex 短码；新 day 在日期为纯 `YYYY-MM-DD` 时使用 `day_YYYYMMDD`，否则回退 `day_` + UUID 短码。文档中的 `pg_001`、`plan_9981`、`sch_0001` 仅为阅读示例。

```typescript
interface ItineraryData {
  trip_info: TripInfo             // 基础行程信息
  preparations: Preparation[]     // 物资准备清单
  bookings: Booking[]             // 预订与交通指南
  food_recommendations: string[]  // 美食推荐清单，由模型生成，不限定范围
  itinerary: DailyItinerary[]     // 每日具体行程安排
  experience_summary?: ExperienceSummary | null
}

interface ExperienceSummary {
  tripTheme?: string
  pace?: string
  intensity?: number
  highlights?: string[]
  weatherSummary?: string
  personalizationTags?: string[]
}

interface TripInfo {
  destination: string           // 目的地（如 "大理、丽江"）
  start_date: string            // ISO 格式（如 "2026-07-09"）
  end_date: string
  date_label: string            // 展示用日期范围（如 "2026.7.9 - 2026.7.12"）
}

interface Preparation {
  category: string              // 类别（如 "证件"、"衣物"）
  items: string                 // 具体内容（如 "身份证、学生证。"）
}

interface Booking {
  type: string                  // 类型（如 "机票（去程）"、"酒店"）
  details: string               // 预订详情建议；涉及实时事实必须基于后端受控事实源，或提示以官方渠道确认为准（见《外部事实源与工具调用规范》七）
}

interface DailyItinerary {
  id: string                    // 稳定 ID（如 "day_20260709"）
  date: string                  // ISO 格式
  title?: string                // 可选日期标题，如 "抵达大理"
  schedules: Schedule[]
}

interface Schedule {
  id: string                    // 稳定 ID
  time_period: string           // 时间段（如 "上午"、"下午"、"晚上"）
  start_time?: string | null    // 可选，24 小时制，如 "09:00"
  end_time?: string | null
  activity: string
  transport?: string | null     // 可选交通方式或备注
  note?: string | null          // 可选补充说明
  place_name?: string | null
  location?: string | null      // 工具返回的 "lng,lat" 等位置文本
  duration_minutes?: number | null
  travel_minutes?: number | null
  distance_km?: number | null
  transport_mode?: "driving" | "transit" | "walking" | "bicycling" | null
  tags?: string[]               // 省略时后端补 []
  booking_required?: boolean    // 省略时后端补 false
  fact_status?: "verified" | "reference" | "unverified" | null
  fact_refs?: string[]          // 请求级 fact_id；省略时后端补 []
  action?: ScheduleAction | null
}

interface ScheduleAction {
  type: "map" | "booking" | "details" | "alternative" | "complete"
  label: string
}
```

命名边界：`experience_summary` 本身仍属于 `ItineraryData` 的 snake_case；其内部六个展示字段按当前 Pydantic alias 与前端类型使用 camelCase。后端同时接受这些字段的 Python snake_case 名。请求可省略有默认值的增强字段；后端真实 `model_dump()` 响应会把 `ExperienceSummary` 的六个默认字段，以及 Schedule 的 nullable 字段、`tags=[]`、`booking_required=false`、`fact_refs=[]` 一并序列化。新增 Schedule 字段只受上述类型/枚举约束；当前业务校验不会额外限制数值正负、经纬度格式、`fact_refs` 是否真实存在或 `fact_status` 与引用事实是否一致。

## 二、业务流程指南

**注意**：本节仅展示数据在各 API 之间流转的宏观顺序；详细任务流程必须严格遵循《任务详细流程规范》。

### 2.1 应用初始化流

```
AppProvider 挂载
  ├── GET /api/postcard-groups  ──→ PostcardGroup[] → 存入缓存
  ├── GET /api/reports          ──→ Report[]        → 存入缓存
  └── GET /api/plans            ──→ Plan[]          → 存入缓存
          ▼
  各 View 按需从缓存消费：
  - postcards-view             消费 PostcardGroup[]（双列瀑布流泡泡框）
  - postcard-collection-view   消费 PostcardGroup.postcards[]
  - reports-view               消费 Report[]（1:1.1 泡泡框网格）
  - history-view               消费 Plan[]（历史规划卡片网格）
```

当前前端使用 Next.js App Router URL 导航，`AppProvider` 在顶层持有三类列表缓存。初始化通过 `Promise.allSettled` 并发请求三类列表：单类失败不会清空另外两类成功结果，页面可按失败类别重试。

### 2.2 旅行后流（上传照片 → AI 生成明信片/报告）

```
主页操作：开关"生成明信片"/"生成报告" → 选照片 → 写需求 → 点"发送"
          ▼
前端：if (generatePostcards 或 generateReport) {
        读取每张照片 EXIF 拍摄时间/地点（读不到置 null）
        → 最多 5 个 worker 并发调 #4 POST /api/images/upload 上传全部照片；
          单张仅在 AppError(1003) 时最多额外重试 2 次
        → 收集 photos: [{ assetId, imageUrl, takenAt, location }]
      }
      → 调 #5 POST /api/generate
          ▼
后端：按《任务详细流程规范》六执行（读隐性特质 → 照片理解 → 按 options 生成 →
      整体成功才入库并绑定原图 → 更新隐性特质）
          ▼
前端收到 { postcardGroup, report }：非 null 者分别追加到对应列表缓存
```

- 图片资源复用、原图绑定、引用计数、物理清理统一按《后端技术栈与全局规范》三执行；本流程只强调 `/api/generate` 成功后必须把本次上传原图绑定到产生的 `PostcardGroup`/`Report`，失败时不得留下孤儿资源。

### 2.3 旅行前流（AI 规划对话 → 保存）

#### 2.3.1 新建规划

```
规划页：写需求 → 点"发送"（仅 message，context 为 null）
  → #6 POST /api/ai/planning
    后端将 message + context + 隐性特质文档（前端无感）+ 必要时受控工具事实包交给模型
  → 返回完整 ItineraryData → 前端全量替换渲染（非增量拼接）
  → 用户可：contentEditable 直接编辑（前端实时同步本地 itineraryData）；
            继续对话（再次调 #6：新输入为 message，当前 itineraryData 为 context）；重复直到满意
  → 点"保存" → 确认弹窗 → #7 POST /api/plans（新建）
    后端从 trip_info 提取 destination/start_date/end_date 入主表字段并完整存 JSON；
    dateLabel 一律由后端统一格式化函数基于 start_date/end_date 生成，trip_info.date_label 仅作模型参考；
    content 由后端按 Jinja2 模板拼接生成；保存成功后更新隐性特质文档
  → 前端追加规划列表缓存
```

注：规划页所有编辑（含 AI 对话产生的修改）均先更新前端本地 itineraryData 副本，仅在用户点"保存"并确认后才发起持久化请求。

#### 2.3.2 继续编辑已有规划

```
历史规划页：点"继续编辑" → 前端从缓存取 plan.itineraryData（零网络开销），记住 plan.id
  → 跳转规划页渲染 → 编辑 + AI 对话（调 #6）同上
  → 点"保存"：有 plan.id → #8 PUT /api/plans/{plan_id}（覆盖，请求体与 #7 完全相同）
  → 后端覆盖旧记录并返回更新后的完整 Plan，更新隐性特质文档 → 前端刷新缓存对应项
```

### 3.4 上传原图

- **Method**: `POST`；**Endpoint**: `/api/images/upload`；**Content-Type**: `multipart/form-data`
- **触发时机**：主页点击"发送"后，只要 `generatePostcards` 或 `generateReport` 任一为 true 且用户已选照片，前端必须先调本接口上传所有照片。
- **Request Payload**：表单字段 `file`: (Binary File Data) — 单张照片原图。
- **前端调用策略**：本接口仅支持单张上传；当前 `AppProvider` 以最多 5 个 worker 并发上传，单张仅在 `AppError(1003)` 时最多额外重试 2 次。任一照片最终失败则整批失败；全部成功后才与本地读取的 `takenAt`、`location` 合并拼装入 #5 的 `photos` 数组。

> 设计理由：本接口只保存图片并返回相对路径，不做图片识别；照片语义识别统一由 #5 结合 `takenAt`/`location` 元信息与多模态模型完成。

**后端安全校验要求**（实现细节主定义见《后端技术栈与全局规范》二与《任务详细流程规范》五）：1. 后端生成 UUID 文件名，不使用用户原始文件名落盘；2. MIME 若提供则必须在 JPEG/PNG/WebP 白名单内；扩展名不在白名单时允许按合法 MIME 推导扩展名；随后检查 15MB 大小上限并用 Pillow 解码验证；3. 物理路径映射防 `..` 穿越；4. 上传成功创建 `temporary` FileAsset，待生成成功绑定后改为 `attached`。

当前实现细节：落盘格式仅为 jpg/jpeg/png/webp，大小上限 15MB；保存前会用 Pillow 做 EXIF 方向修正和适度压缩，最长边超过 2048px 时缩放，JPEG/WebP 使用均衡质量重编码，PNG 做无损优化。只有重编码结果更小时才替换原字节。

**成功响应**:

```json
{ 
  "code": 0, 
  "message": "success", 
  "data": { 
    "assetId": "asset_001", 
    "imageUrl": "/static/uploads/2026/05/abc123.jpg" 
  }
}
```

**失败响应示例**:

```json
{ "code": 1002, "message": "文件类型不支持，仅允许 jpg/png/webp", "data": null }
```

### 3.5 触发 AI 生成（明信片 + 报告）

- **Method**: `POST`；**Endpoint**: `/api/generate`；**Content-Type**: `application/json`；**触发时机**: 主页点击"发送"。
- **失败资源处理**：本次任务失败或异常时，后端必须将请求体中已上传但未绑定的 `temporary` FileAsset 释放或标记待清理，避免孤儿文件（生命周期主定义见《后端技术栈与全局规范》三）。
- **隐性特质读取**：发起多模态请求前必须按 `current_user_id` 读取隐性特质文档作为上下文；生成成功后回写更新（编排见《后端与大模型通信接口规范》九，时序见《任务详细流程规范》六）。
- **原图归属**：生成成功后，本次上传原图必须绑定到产生的 `PostcardGroup`/`Report`（即使未被选为封面），FileAsset 由 `temporary` 改 `attached` 并经 FileAssetService 建引用。
- **整体事务语义**：用户勾选的明信片子流程/报告子流程任一整体失败，则本次整体失败，返回 data=null，严禁持久化半成品 PostcardGroup 或 Report。例外是多张明信片中的单张图片若被 Provider 明确判定为输入内容审核失败：后端先用净化提示重试一次，仍失败则只跳过该张；至少一张成功时继续提交，全部被跳过才返回 1001。其他生成内容类失败为 1001，服务配置、模型权限、AppKey、模型结果下载失败、磁盘落盘失败为 1003。
- **图片生成数量上限**: 本阶段 `PostcardSelectionResult.items.length` 上限为 5，默认 3，具体数量由明信片选图 Prompt 让模型按用户需求判断；后端只做安全边界校验，不从自然语言里自行解析数量。

### 3.8 更新行程规划（覆盖）

### 3.9 删除明信片组

- **Method**: `DELETE`；**Endpoint**: `/api/postcard-groups/{group_id}`；**触发时机**: 明信片页泡泡框菜单"删除"。

**Request URL 示例**: `DELETE /api/postcard-groups/pg_001`

**成功响应**: `{ "code": 0, "message": "success", "data": null }`

**资源不存在响应**: `{ "code": 1004, "message": "明信片组不存在或已被删除", "data": null }`

**后端实现强制要求**：1. 权限校验按《后端技术栈与全局规范》四执行，必须 `WHERE id = :id AND user_id = current_user_id`；2. 删除后必须释放该组及其 postcards 关联的 FileAsset 引用；严禁直接 `os.remove`，必须经 `FileAssetService.release(...)` / `safe_delete_if_unreferenced(...)`，由其判断是否仍被 Report、Plan、隐性特质文档等引用（流程见《任务详细流程规范》十）。

### 3.10 删除报告

- **Method**: `DELETE`；**Endpoint**: `/api/reports/{report_id}`；**触发时机**: 报告页泡泡框菜单"删除"。

**Request URL 示例**: `DELETE /api/reports/rpt_001`

**成功响应**: `{ "code": 0, "message": "success", "data": null }`

**后端实现强制要求**：1. 权限校验同上；2. 特质文档保留：删除历史报告不回滚、不修改隐性特质文档（长期进化偏好不随历史记录删除而失效）；3. 删除后必须释放该报告关联的 FileAsset 引用（coverImage 与本次绑定的原图）；若 coverImage 为 `/static/images/default_cover.jpg` 则不释放；严禁直接删物理文件，必须经 FileAssetService。

### 3.11 删除历史规划

- **Method**: `DELETE`；**Endpoint**: `/api/plans/{plan_id}`；**触发时机**: 历史规划页卡片菜单"删除"。

**Request URL 示例**: `DELETE /api/plans/plan_9981`

**成功响应**: `{ "code": 0, "message": "success", "data": null }`

**后端实现强制要求**：1. 权限校验同上；2. 特质文档保留：删除历史规划不回滚、不修改隐性特质文档；3. 若后续 Plan 绑定 `plan_attachment` 资源，删除时同样必须经 FileAssetService 释放引用，严禁直接删物理文件。
