# 🪐《旅行星球》数据库表结构与迁移规范

> **⚠️ 给 coding agent 的核心系统指令**：
> **本文主定义**：SQLModel 表结构、字段落点、索引、唯一约束、枚举值、Alembic 迁移、SQLite Demo 规则与 PostgreSQL 扩展边界，以及 `tool_call_logs` 表结构。
> **本文不主定义**：对外 DTO 字段（《数据结构与通信接口规范》）；FileAsset 生命周期、状态机、引用矩阵、删除铁律（《后端技术栈与全局规范》三）；任务事务时序（《任务详细流程规范》）；工具使用边界（《外部事实源与工具调用规范》）。
> 严禁因数据库实现方便而修改对外 DTO 字段、删除 `user_id`、绕过 Alembic、绕过 FileAssetReference 或把完整 URL 写入数据库。

## 一、总体设计原则

1. Demo 阶段为单用户、无登录、SQLite；所有核心表保留 `user_id: str`。对外 CRUD 查询/更新/删除按 `current_user_id` 过滤主记录；FileAsset 引用重算、启动基线检查等内部维护查询按资产/owner/系统路径工作，不都附加当前用户条件。
2. 数据库只保存稳定业务事实和相对资源路径：所有资源路径必须以 `/static/` 开头，严禁保存 `http://`、`https://`、`localhost`、内网 IP、第三方临时 URL 或本地绝对物理路径；模型返回的图片必须下载落盘转为本地相对路径后才能入业务表。
3. `file_asset_references` 是引用关系唯一事实来源，`file_assets.ref_count` 只是缓存统计字段（规则主定义见《后端技术栈与全局规范》三）。
4. 所有表结构变更必须经 Alembic revision；严禁业务代码手写 SQL 建表或在 endpoint 中临时建表。

## 二、通用字段规范

1. 主业务实体 `postcard_groups`、`postcards`、`reports`、`plans`、`file_assets`、`user_memories` 包含 `id`、`user_id`、`created_at`、`updated_at`；仅追加型的 `file_asset_references`、`user_memory_events`、`tool_call_logs` 没有 `updated_at`。
2. `id` 为字符串主键，由后端生成：业务前缀 + UUID 短码（`pg_`、`pc_`、`rpt_`、`plan_`、`asset_`、`far_`、`mem_`、`tool_`、`mev_`）；文档示例中的顺序号仅供阅读，严禁依赖自增 ID。
3. Python 默认值由 `utcnow()` 生成 UTC-aware `datetime`，数据库列实际为未声明 `timezone=True` 的 SQLAlchemy `DateTime`；SQLite 读取时不保证保留时区偏移。当前这些审计时间不直接出现在主要页面 DTO 中。
4. `start_date`/`end_date` 数据库列统一为 nullable String。Plan 保存路径强制校验 `YYYY-MM-DD`；照片生成得到的 PostcardGroup/Report 日期当前只经 Pydantic `str | None`，没有额外格式校验，因此表层本身不保证格式。
5. JSON 字段（`chart_data`、`profile_data`、`itinerary_data`、`memory_json`、`delta_json`、工具日志摘要）使用 SQLAlchemy `JSON` 类型：SQLite 下落 TEXT/JSON 兼容存储，PostgreSQL 下可换 JSONB；业务代码只处理 Pydantic 校验后的 dict/list，严禁手拼 JSON 字符串。

## 三、表清单与关系总览

必须实现：`postcard_groups`、`postcards`、`reports`、`plans`、`file_assets`、`file_asset_references`、`user_memories`、`user_memory_events`；启用任何外部工具时必须实现 `tool_call_logs`。

关系概览：一个 PostcardGroup 拥有多张 Postcard；Report 独立存在但可复用明信片生成图或上传原图作封面；Plan 独立存储完整 ItineraryData；FileAsset 与业务实体之间不通过业务表外键表达复用，统一经 `file_asset_references` 表达多对多引用（引用矩阵见《后端技术栈与全局规范》3.2）；UserMemory 与 user_id 一对一保存当前隐性特质文档，UserMemoryEvent 记录增量证据。

用途：所有上传或生成文件资源的资源台账（生命周期与状态机主定义见《后端技术栈与全局规范》三）。

| `mime_type` | String | not null | 如 `image/jpeg` |

| `usage_type` | String | not null | `upload` / `generated_postcard` / `generated_report_cover` / `system` |
| `status` | String | not null | `temporary` / `attached` / `deleted` |
| `ref_count` | Integer | not null, default 0 | 缓存，以引用表统计为准 |
| `storage_backend` | String | not null, default `local` | 预留对象存储 |
| `checksum` | String | nullable | 可选去重/校验 |

| `updated_at` | DateTime | not null | |

## 九、`file_asset_references` 表

用途：文件资源被哪些业务实体引用的**唯一事实来源**。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | String | PK | `far_` + UUID 短码 |
| `user_id` | String | index, not null | 必须与 FileAsset 及业务实体用户一致（系统资产不建引用） |
| `asset_id` | String | FK→file_assets.id, index, not null | |
| `owner_type` | String | index, not null | `postcard_group` / `postcard` / `report` / `plan` / `user_memory` |
| `owner_id` | String | index, not null | |
| `role` | String | not null | `source_photo` / `postcard_image` / `report_cover` / `plan_attachment` / `memory_evidence` |
| `created_at` | DateTime | not null | |

唯一约束：`unique(asset_id, owner_type, owner_id, role)`。除两个复合索引外，`Field(index=True)` 还为 `user_id/asset_id/owner_type/owner_id` 创建 `ix_*` 单列索引（`asset_id` 因此与 `idx_far_asset` 重复）。当前 `attach_with_reference()` 校验资产存在、按唯一元组幂等写入并重算引用数，但不自行查询业务 owner，也不比较传入 `user_id` 与资产用户；所有现有调用都在上游完成当前用户资产校验并使用后端生成的 owner ID。`owner_type/role` 组合没有数据库约束，现有业务调用按《全局规范》3.2 矩阵写入。

## 十三、枚举值统一表

`FileAsset.usage_type`：`upload`、`generated_postcard`、`generated_report_cover`、`system`。`FileAsset.status`：`temporary`、`attached`、`deleted`。`FileAssetReference.owner_type`：`postcard_group`、`postcard`、`report`、`plan`、`user_memory`。`FileAssetReference.role`：`source_photo`、`postcard_image`、`report_cover`、`plan_attachment`、`memory_evidence`。`user_memories.last_source_type` / `user_memory_events.source_type`：`generate`、`plan_save`、`plan_update`、`manual`。`tool_call_logs.status`：`success`、`timeout`、`failed`、`fallback`。

上述值是当前代码写入/DTO 接受的集合。数据库列均为普通 String，没有 `CHECK` 约束；`file_asset_service` 也不统一校验任意调用方传入的 `usage_type/owner_type/role`，因此一致性依赖现有受控调用路径。

## 十四、Alembic 迁移规范

1. 当前迁移链为 `a719304102bf (init_schema) → b824c31f5a21 (reports.profile_version/profile_data)`。严禁以业务代码中的 `SQLModel.metadata.create_all()` 作为正式建表方式；Demo 可提供“一键初始化”脚本，但其内部必须执行 `alembic upgrade head`。
2. 推荐流程：改 SQLModel 实体 → `alembic revision --autogenerate -m "..."` → 人工检查脚本（索引、唯一约束、JSON 类型、nullable、默认值）→ `alembic upgrade head` → 提交 migration 文件。严禁提交本地手工演化的 SQLite 文件作为结构来源。
3. 迁移文件必须可在空库重复执行；默认数据初始化（demo 用户记忆文档、系统默认图 FileAsset）通过单独 seed 脚本或启动检查创建，严禁在 migration 中写死本机绝对路径。

## 十五、SQLite Demo 开发规则

1. 数据库放 `data/travelplanet.db`，配置 `DATABASE_URL=sqlite:///./data/travelplanet.db`；`data/` 目录与 SQLite 文件不提交仓库，仓库只提交 `.env.example`、迁移脚本与 seed 逻辑。
2. SQLite 外键默认未开启：必须通过 SQLAlchemy 连接事件启用 `PRAGMA foreign_keys=ON`；即便启用，业务删除仍必须经 Service 以保证引用释放与物理清理。
3. 启动时 `ensure_demo_baseline()` 检查 `DEFAULT_USER_ID` 的 `user_memories` 与系统默认图 FileAsset，不存在则创建；默认封面物理文件不存在时会用 Pillow 生成 1024×1024 JPEG 占位图。表尚未迁移时启动检查只记录错误并回滚，不代替 `alembic upgrade head`。

## 十六、PostgreSQL 扩展预留

代码层必须 SQL 方言中立：严禁 SQLite 专属 SQL；JSON 字段经 SQLAlchemy JSON 抽象；索引与唯一约束用 Alembic 可迁移写法。未来切换 PostgreSQL 时，JSON 字段可迁 JSONB、常用查询字段可加 GIN 或表达式索引、日期字段可迁 Date；但对外 DTO、`user_id`、相对路径、引用表机制、标准响应体与业务流程均保持不变。

## 十七、删除、级联与事务边界

1. 业务删除由 Service 主导，严禁依赖数据库 cascade 完成全部副作用；删除 PostcardGroup/Report/Plan 必须释放相关引用，再由 FileAssetService 重新统计 ref_count 并决定物理处理。
2. `/api/generate` 整体成功或整体失败：模型调用与文件准备阶段严禁持有事务；最终写入 PostcardGroup、Postcard、Report、引用与资产状态变更使用短事务；短事务失败时已下载生成图按 `temporary` 交 FileAssetService 清理（时序主定义见《任务详细流程规范》六）。
3. Plan 保存/更新事务只包数据库写入与必要同库状态变更；隐性特质更新在 Plan 成功保存后以独立事务处理，记忆失败严禁回滚已保存 Plan，但必须记录错误。

## 十八、实现验收清单

数据库实现复核项：核心表有 `user_id`；对外主记录 CRUD 有用户过滤；对外 camelCase 由 DTO 层转换；业务表不保存完整资源 URL；引用以 `file_asset_references` 为事实来源；Alembic 两个 revision 能在空 SQLite 库升级到 head；`plans.itinerary_data` 与 `reports.chart_data/profile_data` 使用 JSON；旧报告允许两个 profile 字段为 null；基线初始化可创建 demo 记忆与系统默认图；Plan 日期保存前校验 `YYYY-MM-DD`；工具调用尽力写 `tool_call_logs`。
