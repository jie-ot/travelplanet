# 🪐《旅行星球》任务详细流程规范

> **⚠️ 给 coding agent 的核心系统指令**：
> **本文主定义**：每个后端业务任务的端到端执行流程、入口接口与模块落点、模型可决策/禁止决策边界、后端强制校验、事务边界、失败处理、隐性特质读取与更新闭环。
> **本文不主定义**：接口字段/DTO/响应体/错误码（《数据结构与通信接口规范》，下称《接口规范》）；目录/路径/FileAsset 生命周期/鉴权（《后端技术栈与全局规范》，下称《全局规范》）；模型调用与解析（《后端与大模型通信接口规范》，下称《模型规范》）；外部工具（《外部事实源与工具调用规范》，下称《工具规范》）。
> coding agent 严禁因本文流程描述而新增、删除或改名任何前后端接口字段。

## 一、总原则：后端是导演，大模型是受控语义专家

本项目核心是"懂用户的旅行助手"。所有产生用户内容、生成结果或长期偏好影响的任务，必须围绕"当前请求 + 用户隐性特质文档 + 可验证事实 + 结构化校验"展开。后端负责流程、资源、事务、校验、工具白名单和入库；大模型只负责照片理解、语义筛选、风格判断、文案生成、规划重写和记忆增量建议。模型**可以**决策审美、偏好、旅行语义、照片选择、文案与规划内容；模型**严禁**决策数据库结构、文件路径、FileAsset 生命周期、最终响应字段、错误码、事务提交与工具事实可信度。严禁把所有输入丢给模型让其自由决定数据库写入、文件路径、接口响应、资源引用或工具接入。

通用纪律：1. 所有对外业务路由注入 `current_user_id`；主业务记录按 `user_id == current_user_id` 查询，生成/规划再按该用户读取隐性特质；2. 生成成功及 Plan 保存/更新成功后合并隐性特质增量，删除/列表/上传不更新记忆，当前也不为删除写记忆事件；3. JSON 模型输出经 `output_parser.py` 与 Pydantic 校验，再由 Service 做对应业务校验；图片模型 URL 则只由图片 client 提取并立即交 storage 落盘；4. 外部事实只能经白名单工具或本地 B 类指引进入规划上下文；5. 当前业务日志会保存有界的用户/模型/照片语义/错误摘录，明信片阶段还保存完整组合 Prompt，因此日志必须作为敏感本地数据保护。

## 二、通用模块职责（细节主定义见《全局规范》七与《模型规范》三）

`api/endpoints/*.py` 只做依赖注入、参数接收、调 Service、返回标准响应体；`app/services/` 负责确定性业务流程（请求校验、事务、FileAsset 绑定/释放、路径映射、文件 I/O、Markdown 生成、ItineraryData 业务校验、稳定 ID 对齐、隐性特质合并、事实包聚合）；`app/ai/orchestrator.py` 负责模型编排（读 prompts、调 clients、经 output_parser 解析、返回 schemas 约束的结构化对象），严禁直接写业务表或管理 FileAsset；`app/ai/memory/context_builder.py` 组装隐性特质摘要 + 当前请求 + 照片语义 + 规划 context + 事实包；`app/services/memory_service.py` 负责隐性特质文档读取、创建、合并、版本更新与持久化；`app/services/travel_fact_service.py` 是外部事实源唯一聚合入口（见《工具规范》五）。

## 三、通用前置与收尾流程

对外请求先由 FastAPI/Pydantic 校验并注入 `current_user_id`。主记录 CRUD 使用用户过滤；生成与规划在模型调用前读取或创建记忆，Plan 保存/更新在业务记录提交后的记忆合并事务中读取或创建记忆。涉及本地静态文件的路径经 `/static/...` 白名单映射；模型返回的临时公网图片 URL 仅用于后端下载，不入库、不返回前端。

所有 AI 写任务成功后必须完成通用收尾：1. 模型输出结构化解析与校验；2. 业务规则二次校验；3. 短事务写库；4. 经 `MemoryService.merge_memory_update(...)` 合并模型提议或确定性记忆增量；5. 返回《接口规范》标准响应体。`/api/generate` 会提前并行计算记忆提议，但只在业务入库成功后合并；Plan 保存/更新直接生成确定性目的地偏好增量，不调用模型。记忆合并使用独立事务，失败只记录日志，不回滚已经成功的业务结果。

失败处理统一遵循：参数、路径、归属校验失败 → `1002`；模型生成、内容审核、限流/额度、空内容、JSON 校验、图片生成失败 → `1001`；服务配置、模型权限、AppKey、模型结果下载失败、磁盘落盘失败 → `1003`；业务主记录不存在 → `1004`。已上传未绑定的临时文件、已下载未入库的生成图，必须交由 `FileAssetService` 释放或标记待清理。

## 四、任务 1：应用初始化列表读取

涉及接口：`GET /api/postcard-groups`、`GET /api/reports`、`GET /api/plans`；入口分别为 `endpoints/postcard_groups.py`、`reports.py`、`plans.py`；业务分别进入 `postcard_service.py`、`report_service.py`、`plan_service.py`。

固定流程：1. 注入 `current_user_id`；2. 按 `user_id` 过滤查询列表；3. 按 `created_at desc` 排序；4. 转换为《接口规范》DTO；5. 空数据返回 `data=[]`；6. 不调用大模型、不调用工具、不更新隐性特质。

约束：这是只读任务，严禁因为"做懂用户"而隐式改变画像；若未来需要个性化欢迎语，必须另设接口。

## 五、任务 2：上传原图

涉及接口：`POST /api/images/upload`；入口 `endpoints/images.py`；文件校验与落盘 `storage_service.py`；FileAsset 记录 `file_asset_service.py`。

固定流程：1. 注入 `current_user_id`，接收单个 `UploadFile`；2. MIME 若提供则校验为 JPEG/PNG/WebP；文件名扩展名不受支持时可按合法 MIME 推导，随后校验非空、15MB 上限并用 Pillow 解码；3. 后端生成 UUID 文件名；4. 做 EXIF 方向修正、最长边 2048px 缩放和适度重编码（仅在结果更小时采用）；5. 保存到 `/static/uploads/{yyyy}/{mm}/{uuid}.{ext}`；6. 创建 `FileAsset(usage_type="upload", status="temporary", ref_count=0)`；7. 返回 `{ assetId, imageUrl }`。

模型参与：无；隐性特质：不读取、不更新（用户可能只上传不生成）。

失败处理：类型不支持、超限、解码失败、路径非法 → `1002`；磁盘写入失败或配置错误 → `1003`；文件已写入但 FileAsset 创建失败时，必须删除或标记待清理该物理文件。

## 六、任务 3：触发 AI 生成（明信片 + 报告）

涉及接口：`POST /api/generate`；入口 `endpoints/generate.py`；主流程 `generation_service.py`；照片分析、明信片选图与创意、报告草稿、记忆增量由 `ai/orchestrator.py` 编排；图片下载落盘 `storage_service.py`；引用 `file_asset_service.py`。当前实现会在不改变接口同步返回语义的前提下，用受控线程池并行报告草稿、明信片生成、文件读取与记忆增量提议。

### 6.1 通用固定流程

1. 注入 `current_user_id` 并接收请求；
2. 校验 `options.generatePostcards`/`options.generateReport` 至少一个 true，否则 `1002`；
3. 校验 `photos.length > 0`；
4. 逐张校验 `photos[].assetId` 属于当前用户且内部 `FileAsset.relative_path == photos[].imageUrl`；
5. 校验路径以 `/static/uploads/` 开头且不含 `..`；
6. 读取隐性特质文档；
7. 调用照片理解模型生成 `PhotoAnalysisResult`（当前最多 5 张一批，多批按配置并行，随后按原始 asset 顺序合并）；
8. 按 options 进入明信片子流程和/或报告子流程；
9. 所有被勾选任务均成功后，**短事务**统一写入 PostcardGroup、Postcard、Report、FileAssetReference，并将实际获得引用的本次生成图与上传原图状态置为 `attached`（两段式规则见《全局规范》3.1，引用归属见其 3.2 引用矩阵）；
10. 取得并合并前面并行计算的隐性特质增量；
11. 返回固定含 `postcardGroup` 与 `report` 的响应，未生成者为 `null`。

事务边界：整体成功或整体失败语义——任一被勾选任务失败则整体 `data=null`，严禁持久化半成品；错误码按本文第三节统一映射，生成内容类失败为 `1001`，配置、权限、下载或落盘类失败为 `1003`。模型调用、工具调用、文件下载落盘阶段严禁持有数据库事务；只在最终写库阶段开启短事务；短事务失败时，本次所有 `temporary` 生成图与未绑定原图交 `FileAssetService` 释放或标记待清理。

### 6.2 照片理解阶段

输入：本次照片的本地 base64 data URL、`takenAt`、`location`、必要的需求摘要（传图流程见《模型规范》五）；输出：`PhotoAnalysisResult`。

模型可决策：每张照片的场景摘要、主体、构图、氛围、地点与时间线推断、是否适合做明信片/报告素材及原因。模型禁止：生成最终图片路径；声称照片属于他人；输出本次 `photos` 之外的 assetId；把图片语义全文写入普通日志。多批分析合并时若缺失、重复或出现非本次 assetId，整体按生成失败处理。

后端强制校验：输出 `assetId` 必须全部来自本次请求；数组非空；字段类型符合 `schemas.py`；无效照片可标记不适合，但不得导致路径绕过或资源遗漏。

### 6.3 明信片生成子流程

固定流程：1. 基于 `PhotoAnalysisResult + requirements + 隐性特质` 调用选图模型生成 `PostcardSelectionResult`；2. 将全部已选原图按 assetId 标注后作为一次多模态输入，创意模型在单次请求内先比较至少 3 个不同方向并只输出最佳方案，生成包含核心概念、原图改造、视觉记忆点、字体层级、标题、0–2 条可选辅助文案和 Seedream 指令的 `PostcardPlanResult`；3. 两个阶段均执行 Pydantic 与业务字段校验，JSON 或字段不合法时各重试一次；4. 逐张调用图生图模型，参考图必须来自选中上传原图的本地 base64（见《模型规范》六），多张图按 `GENERATION_IMAGE_PARALLELISM` 并行；Provider 明确拒绝输入内容时，单张先用固定净化 Prompt 重试一次，仍拒绝则只跳过该张；5. 下载成功图的模型临时 URL 到 `/static/generated/postcards/{yyyy}/{mm}/{uuid}.{ext}` 并创建 temporary FileAsset；6. 最终短事务中写 PostcardGroup、成功的 Postcard，创建 `postcard/postcard_image` 引用并将资产转 `attached`。

模型可决策：选哪些照片做参考图；创意阶段在看到已选原图后决定核心概念、原图改造方式、唯一视觉记忆点、字体层级、标题、可选辅助文案和最终生图指令。Seedream 可在明确艺术指导内微调比例、裁切和装饰细节，但不得代替创意模型作出核心版式与字体层级决策。模型禁止：把用户需求原文直接丢给图片模型；生成最终 `imageUrl`；请求纯文生图；引用本次 photos 之外的图片；要求生成文字水印。

失败处理：普通图片生成失败、下载失败、落盘失败、校验失败仍会使整个 `/api/generate` 失败；图片生成/校验失败映射 `1001`，下载/落盘失败映射 `1003`。只有 `ImageInputPolicyError` 经净化 Prompt 重试后仍失败时允许按张跳过；至少一张成功则继续，全部被跳过才返回 `1001`。已下载但最终未提交的文件按 `temporary` 清理。

### 6.4 报告生成子流程

固定流程：1. 基于 `PhotoAnalysisResult + requirements + 隐性特质` 调用报告草稿模型生成含 `profile_data` 的 `ReportDraftResult`；2. Pydantic 校验字段类型，Service 额外要求 `location/personality_summary/content` 非空；当前没有单独校验报告草稿日期格式；3. `content` 去空白后 180–240 字且非空行必须是引言、三个 `瞬间X｜`、`人格判词｜` 共五段；`chart_data` 必须按固定顺序完整包含五维且分值 0–100；`profile_data` 必须有四条固定顺序光谱（0–100）、3–5 个关键词、恰好 3 个正文各 30–60 字的模块；4. 封面规则：同时生成明信片 → `coverImage` 用第一张成功明信片图；仅生成报告 → 使用请求中第一张上传照片；无可用图片 → `/static/images/default_cover.jpg`；5. `/static/generated/reports/...` 与 `generated_report_cover` 为预留能力，当前不生成 AI 报告封面；6. 写库时 Report 的 `location/start_date/end_date` 取报告草稿字段，`date_label` 取照片分析日期生成的本次任务标签，`profile_version=2`，`profile_data` 以 camelCase JSON 写入；创建 `report/report_cover` 与所有 `report/source_photo` 引用（默认图不建引用）。

模型可决策：人格摘要、报告正文、雷达图分值、照片与长期偏好的关系解释。模型禁止：输出 DTO 之外字段；输出五维之外的雷达图项；把隐性特质全文原样暴露在正文；声称已验证不可验证的现实事实。

### 6.5 隐性特质更新

只有所有被勾选任务整体成功并完成入库后才允许合并记忆：1. 当前实现会生成一个保守的 `MemoryUpdateResult` 提议，证据摘要聚焦“用户在某目的地完成一次旅行内容生成”；2. 仅输出新增偏好、弱化偏好、证据摘要、置信度、来源任务；3. `memory_service.py` 以确定性规则合并并递增版本；4. 严禁模型直接覆盖整个历史文档；5. 严禁把隐性特质全文写入普通日志。记忆合并失败不回滚已成功入库的业务数据，但必须记录可排查日志。

## 七、任务 4：AI 行程规划对话

涉及接口：`POST /api/ai/planning`；入口 `endpoints/ai_planning.py`；主流程 `planning_service.py`；事实聚合 `travel_fact_service.py`；上下文组装 `ai/memory/context_builder.py`；模型生成 `ai/orchestrator.py`；校验 `itinerary_validation_service.py` 与 `itinerary_id_service.py`。

固定流程：1. 注入 `current_user_id`，接收 `message + context`；2. 校验 `message` 非空、`context` 为 `ItineraryData | null`；3. 读取隐性特质文档，并在系统提示中注入北京时间当前日期；4. `needs_facts()` 当前恒为 false，首轮不构造或注入 `TravelFactPack`，`context_builder.py` 组装 `message + context + 隐性特质摘要`；5. 进入受限研究协议（最多 8 个模型研究轮次、研究阶段最多 75 次外部 tool call）：模型必须先 `declare_trip_scope`，再调用五个白名单外部工具，并可用 `update_planning_fact_state` 选择保留事实和列出 `remainingQueries`；外部候选事实获请求级 `fact_id`，相同工具和参数命中请求内缓存；6. 信息足够后模型必须在不含外部查询的单独一轮调用 `finish_research`，否则研究失败；7. 工具关闭后，用声明范围、保留事实与研究摘要无工具生成完整 `ItineraryData`，解析失败只进行一次无工具 JSON 修复；8. 对初稿做一次低温审稿，可提出最多 8 个白名单补查；若获得新增事实则完整重生成一次，审稿无效或无新增事实时保留初稿；9. `itinerary_validation_service.py` 先只重排具有可解析 `start_time` 的条目，未解析时间条目保持原位置；10. `itinerary_id_service.py` 做稳定 ID 对齐；11. 业务校验目的地与起止日期、每日日期范围及连续递增、`itinerary` 和每天 `schedules` 非空、已有准备/预订项字段非空、ID 同层不重复；可解析时间用于结束不早于开始及起始时间递增校验，格式不合法的非空时间字符串会被当作不可解析而跳过；12. 返回完整 `ItineraryData`。当前 Service 不要求行程覆盖起止范围的首尾每一天，不校验 `food_recommendations`、增强 Schedule 数值/位置、`fact_refs` 真实性或正文中的航班号/票价。

模型可决策：行程安排、每日节奏、活动描述、饮食建议、准备清单、预订指南表达方式、如何结合长期偏好调整节奏风格。模型禁止：返回 Markdown 或局部 patch；改变 ItineraryData 字段结构；编造实时航班号、票价、余票、酒店可订状态、当天政策、天气预报；把事实包之外的信息写成已验证事实（措辞约束见《工具规范》七）。

事务边界：本任务只读不写业务表，无数据库事务；工具调用失败一律降级、不导致接口失败（见《工具规范》九）。失败处理：参数失败 `1002`；模型失败/JSON 校验失败（含修复重试后仍失败）`1001`；配置错误 `1003`。

隐性特质策略：对话本身只返回候选 `ItineraryData`，**不更新画像**；只有用户保存规划成功后才更新，避免随口试探造成画像漂移。

## 八、任务 5：保存行程规划（新建）

涉及接口：`POST /api/plans`；入口 `endpoints/plans.py`；主流程 `plan_service.py`；Markdown 生成 `markdown_service.py`；日期展示 `date_label_service.py`；记忆更新由 `plan_service.py` 调用 `memory_service.py` 完成。

固定流程：1. 注入 `current_user_id`，接收 `itineraryData`；2. Pydantic 校验结构符合《接口规范》1.9；3. Service 使用与规划返回相同的日期、行程/日程非空、已有项字段、ID 与可解析时间顺序校验；`preparations`、`bookings`、`food_recommendations` 本身允许空数组；4. 从 `trip_info` 提取 `destination/start_date/end_date`；5. 后端统一生成 `dateLabel`（不采用 `trip_info.date_label` 作为对外字段）；6. Jinja2 使用 `app/services/templates/plan_content.md` 遍历生成 `content`；7. 短事务写入 Plan；8. 保存成功后在独立事务中确定性加入 `目的地偏好：{destination}`，置信度输入为 0.3，来源为 `plan_save`；9. 返回完整 Plan。

模型参与边界：保存与保存后的记忆更新均不调用模型。失败处理：结构/业务校验失败 `1002`；未被业务异常包装的数据库错误由全局处理器映射 `1003`；记忆更新失败不回滚已保存 Plan，记录错误日志后仍返回成功。

## 九、任务 6：更新行程规划（覆盖）

涉及接口：`PUT /api/plans/{plan_id}`；入口与主流程同任务 5，语义为覆盖。

固定流程：1. 注入 `current_user_id`；2. 按 `id + current_user_id` 查询 Plan，找不到返回 `1004`；3. 校验新 `itineraryData`（同任务 5 第 2-3 步）；4. 重新提取 location/startDate/endDate 并重新生成 dateLabel；5. 重新生成 Markdown `content`；6. 短事务覆盖旧记录，严禁新建重复 Plan；7. 成功后基于更新后的最终 itineraryData 合并隐性特质增量；8. 返回更新后的完整 Plan。

补充约束：稳定 ID 在 `/api/ai/planning` 返回前已对齐；保存阶段仍必须校验 ID 存在且类型正确，但不再让模型调整 ID。模型参与边界与失败处理同任务 5。

## 十、任务 7：删除明信片组

涉及接口：`DELETE /api/postcard-groups/{group_id}`；入口 `endpoints/postcard_groups.py`；主流程 `postcard_service.py`；资源释放 `file_asset_service.py`。

固定流程：1. 注入 `current_user_id`；2. 按 `id + current_user_id` 查询 PostcardGroup，找不到返回 `1004`；3. 查询该组 postcards；4. 短事务删除业务记录并释放引用：`FileAssetService.release(owner_type="postcard_group", owner_id=id)` 加上每张 postcard 的 `release(owner_type="postcard", owner_id=pc.id)`；5. `FileAssetService` 重新统计各资产引用，判断是否仍被 Report、Plan、user_memory 等引用；6. 无引用才物理删除或标记待清理；7. 返回 `data=null`。

模型参与：无。隐性特质策略：不回滚、不重写正文；当前删除流程不写 `user_memory_events`。

## 十一、任务 8：删除报告

涉及接口：`DELETE /api/reports/{report_id}`；入口 `endpoints/reports.py`；主流程 `report_service.py`。

固定流程：1. 注入 `current_user_id`；2. 按 `id + current_user_id` 查询 Report，找不到返回 `1004`；3. 短事务删除 Report 并释放该报告全部引用（`report_cover` 与 `source_photo`）；4. 若 coverImage 为 `/static/images/default_cover.jpg`，跳过封面释放（系统资产规则见《全局规范》3.1 第 6 条）；5. `FileAssetService` 重新统计并按需清理；6. 返回 `data=null`。

模型参与：无。隐性特质策略：不回滚、不修改正文；当前删除流程不写审计事件。

## 十二、任务 9：删除历史规划

涉及接口：`DELETE /api/plans/{plan_id}`；入口 `endpoints/plans.py`；主流程 `plan_service.py`。

固定流程：1. 注入 `current_user_id`；2. 按 `id + current_user_id` 查询 Plan，找不到返回 `1004`；3. 短事务删除 Plan；4. 若未来绑定 `plan_attachment` 资源，释放对应引用；5. 返回 `data=null`。

模型参与：无。隐性特质策略：不回滚、不修改正文；用户曾确认保存的规划已是长期偏好证据，删除列表记录不代表偏好失效。

## 十三、任务 10：隐性特质文档维护

隐性特质文档是"懂用户"的核心资产，存于 `user_memories` 表（结构见《数据库表结构与迁移规范》十）。

读取流程：1. `MemoryService.get_or_create_current_memory(current_user_id)` 查询；2. 不存在则创建空白初始文档（version=1，如"暂无稳定偏好，需从后续旅行照片和规划中逐步学习"）；3. 提供给 `context_builder.py` 时必须为摘要或结构化片段，严禁全文无节制塞入 Prompt；4. 全文严禁写入普通日志、严禁返回前端。

更新流程：1. `/api/generate` 由模型生成 `MemoryUpdateResult`，Plan 保存/更新由 Service 构造确定性目的地偏好增量；2. 模型提议先经 Pydantic 校验；3. `MemoryService` 按确定性规则合并并递增 `version`，记录 `last_source_type`/`last_source_id`；4. 每次成功合并固定追加一条 `user_memory_events`；5. 合并失败不得回滚已成功的业务操作，但必须记录错误日志。

触发矩阵：`generate` 成功 → 更新；`plan_save`/`plan_update` 成功 → 更新；规划对话、删除、列表读取、上传 → 不更新且当前不写记忆事件。禁止事项：模型直接覆盖整个历史文档；把失败生成结果写入长期记忆；把全文返回前端；因只读行为更新画像。

**隐性特质合并算法主定义**：`memory_json.preferences` 是结构化事实源，`memory_text` 由其中未标记 `weakened` 的偏好按置信度降序渲染。偏好键使用去首尾空格并转小写后的完整文本做精确匹配；命中时置信度固定增 0.15、证据数加一，未命中时以 `min(输入置信度, 0.5)` 新建；弱化只对精确命中的键减 0.15，降至 0.2 及以下时标记 `weakened`。当前代码不做语义相似、相反偏好调和或自动删除。每次调用都会 `version += 1` 并写一条 `user_memory_events`，即使增量数组为空也如此。

## 十四、任务 11：受控外部事实源、MCP 与 Function Calling

Provider 白名单、工具 Schema、配置项、降级状态、措辞约束、日志边界与禁止事项**全部主定义于《工具规范》**，本文只锁定接入位置与时序：1. 当前 `needs_facts(...)` 恒为 false，`build_fact_pack(...)` 只是返回空兼容包，正常规划不会预取或注入它；2. 外部事实只在研究协议中由模型提出白名单 Function Calling，并一律经 `travel_fact_service.py` 校验执行，endpoint 与普通业务组件严禁直接调用；3. 外部结果以紧凑 JSON 回填，候选事实注册 `fact_id`，最终只把模型保留的完整事实交给无工具生成阶段；4. 状态为 `provider_not_connected`、`unknown`、`needs_official_confirmation` 时，模型必须写成“建议官方确认”类措辞；5. 每次外部调用、参数错误和白名单错误都尽力写入 `tool_call_logs`，日志写入失败不得影响规划接口。

## 十五、任务 12：FileAsset 清理与一致性维护

当前没有全库扫描接口、启动扫描、定时任务或“超过 24 小时”的清理作业。现有清理只发生在明确业务路径：生成失败调用 `discard_temporary(asset_ids)`；删除业务实体调用 `release_and_cleanup(owner_type, owner_id)`；二者都会以 `file_asset_references` 重算 `ref_count`，无引用时尝试删除物理文件并把资产标记为 `deleted`、写入 `deleted_at`。物理文件本来就不存在或删除失败不会使业务接口崩溃，但当前仍会把无引用资产标记为 `deleted`。

模型参与：无；隐性特质：不更新。任何业务 Service 仍严禁直接 `os.remove()`，必须经 FileAssetService 统一方法。

## 十六、验收要点

复核任务时检查：endpoint 是否保持薄层；用户可见主记录是否按 `user_id` 隔离；持久化资源路径是否为 `/static/...`；结构化模型输出是否经解析与 Pydantic；模型/工具调用期间是否未持有长事务；失败是否不写半成品业务记录；FileAsset 引用数是否按引用表重算；记忆触发矩阵是否符合本文；模型是否只能提出白名单 Function Calling 而不能直接联网或写库。
