## 一、配置与环境

1. **严禁硬编码**：业务代码中严禁出现 `localhost`、`127.0.0.1`、具体 IP、AppKey、模型名、外部 URL、超时数值；全部从 `app/core/config.py`（Pydantic Settings）读取，真实值放后端根目录 `.env` 或部署环境变量；仓库只提交 `.env.example`，严禁提交 `.env`。
2. **必备配置项**（模型相关见《后端与大模型通信接口规范》二，工具相关见《外部事实源与工具调用规范》六）：

```env
HOST=0.0.0.0
PORT=8000
FRONTEND_ORIGINS=http://localhost:3000
PUBLIC_BASE_URL=
DATABASE_URL=sqlite:///./data/travelplanet.db
DEFAULT_USER_ID=demo_user_001
STATIC_ROOT=./static
```

3. **启动方式**：`uvicorn.run(app, host=settings.HOST, port=settings.PORT)`；前端 Demo 跑在 3000 端口。
4. **CORS**：`app/main.py` 全局挂载 `CORSMiddleware`，`allow_origins` 按逗号解析 `settings.FRONTEND_ORIGINS`；解析结果为空时当前实现回退为 `["*"]`。默认配置为 `http://localhost:3000`，部署时通过环境变量替换。
5. **PUBLIC_BASE_URL 边界**：仅预留给未来确需生成公网完整 URL 的场景；当前业务表、前后端 API、FileAsset 记录均**严禁**保存完整 URL。
6. 前端环境变量与 `apiClient` 拼接规则主定义见《数据结构与通信接口规范》0.1；后端不得因前端部署方式在业务代码中写死域名或 `/api` 代理细节。
7. `Settings` 类默认值与仓库 `.env.example` 的示例值并不完全相同：代码默认 `VIVO_TEXT_TIMEOUT_SECONDS=75`、`PHOTO_ANALYZE_PARALLELISM=5`、`GENERATION_IMAGE_PARALLELISM=2`，而当前 `.env.example` 分别示例为 `120/10/5`；复制模板为 `.env` 后以环境值为准。规范不得把模板示例误写成类默认值。
8. MCP 启动还使用 `MCP_WAIT_READY_ON_STARTUP`、`MCP_STARTUP_TIMEOUT_SECONDS`、`MCP_UNAVAILABLE_TTL_SECONDS`。当前类默认和 `.env.example` 均令 `MCP_WAIT_READY_ON_STARTUP=true`；应用启动会等待已启用的铁路 MCP 进入 `ready/failed`，最多约 `MCP_STARTUP_TIMEOUT_SECONDS + 1` 秒，失败只记录并降级，不阻止应用启动。

## 二、静态资源与路径铁律（主定义）

1. **相对路径唯一原则**：数据库、API Request/Response、FileAsset 记录中的资源路径**必须且只能**是以 `/static/` 开头的相对路径；严禁出现 `http://`、`https://`、`localhost`、内网 IP、模型侧临时 URL、本地绝对物理路径。
2. **四类合法路径前缀**（当前实现白名单，不得随意新增）：用户上传原图 `/static/uploads/{yyyy}/{mm}/{uuid}.{ext}`；AI 生成明信片 `/static/generated/postcards/{yyyy}/{mm}/{uuid}.{ext}`；预留 AI 报告封面 `/static/generated/reports/{yyyy}/{mm}/{uuid}.{ext}`；系统图片 `/static/images/...`（当前业务使用 `/static/images/default_cover.jpg`）。
3. **落盘文件名**：必须由后端生成 UUID 文件名，严禁使用用户原始文件名。
4. **安全映射**：后端做本地文件 I/O 时，必须将 `/static/...` 经唯一的路径映射工具函数（建议 `app/services/storage_service.py` 内 `resolve_static_path()`）映射到 `STATIC_ROOT`；映射前必须校验：以四类合法前缀之一开头、不含 `..`、规范化后仍位于 `STATIC_ROOT` 之内；任何不合规路径必须拒绝并按 `code=1002` 处理。
5. **静态暴露**：`app/main.py` 必须显式 `app.mount("/static", StaticFiles(directory=settings.STATIC_ROOT), name="static")`。
6. 模型返回的图片一律是临时公网 URL，必须先下载落盘转为本地相对路径才能入库；传图给模型一律走本地文件 base64，细节见《后端与大模型通信接口规范》五、六。

## 三、FileAsset 生命周期（主定义）

### 3.1 状态机与基本规则

1. 所有上传或生成的文件**必须**记录到 `file_assets` 表，由 `FileAssetService` 统一管理生命周期；表结构见《数据库表结构与迁移规范》八、九。
2. 状态机固定为三态：`temporary`（已落盘、未绑定业务记录）→ `attached`（已被至少一个业务实体引用）→ `deleted`（标记删除，待物理清理）。状态迁移只允许由 `FileAssetService` 执行。
3. **统一两段式落盘规则**：无论上传原图还是模型生成图，物理落盘成功后一律先创建 `status="temporary"` 的 FileAsset；只有在业务最终短事务中创建 `FileAssetReference` 成功时，才同事务将状态改为 `attached`。严禁创建"attached 但无引用"的资产。生成任务失败时，所有本次产生的 `temporary` 资产交由 `FileAssetService` 释放或标记待清理。
4. **引用唯一事实来源**：`file_asset_references` 表是引用关系的唯一事实来源；`file_assets.ref_count` 只是缓存统计字段，必须在每次创建/释放引用后由 `FileAssetService` 按引用表重新统计同步，业务代码严禁直接修改。
5. **物理删除铁律**：业务 Service 严禁直接调用 `os.remove()`；必须统一调用 `FileAssetService.release(owner_type, owner_id)`（按 owner 释放全部引用）与 `safe_delete_if_unreferenced(asset_id)`（重查引用表，确认无引用后才物理删除或标记 `deleted`）。物理文件缺失时不得使业务接口崩溃，应记录日志并修正状态。
6. **系统资产**：`/static/images/default_cover.jpg` 对应 FileAsset 的 `user_id` 固定为 `"system"`、`usage_type="system"`、`status="attached"`；该资产**不创建业务引用、不参与释放与物理删除**，任何引用 `default_cover.jpg` 作为封面的业务实体在删除时直接跳过封面释放。

### 3.2 引用矩阵（唯一裁决表）

| owner_type | role | 指向的资产 | 创建时机 |
|---|---|---|---|
| `postcard_group` | `source_photo` | 本次生成所用的全部上传原图 | `/api/generate` 最终短事务 |
| `report` | `source_photo` | 同上（仅当本次生成了报告） | 同上 |
| `postcard` | `postcard_image` | 该明信片的生成图 | 同上 |
| `report` | `report_cover` | 报告封面（当前实现复用第一张明信片生成图、或第一张上传原图、或默认图；`generated_report_cover` 为预留能力，默认图除外） | 同上 |
| `plan` | `plan_attachment` | 预留 | 预留 |
| `user_memory` | `memory_evidence` | 预留 | 预留 |

说明：1. 生成图引用**只**挂在 `owner_type="postcard"` 上，严禁再以组为 owner 对同一生成图重复建引用；删除组时由 Service 遍历子明信片逐一释放；2. 封面复用第一张明信片图时，同一资产同时拥有 `postcard/postcard_image` 与 `report/report_cover` 两条引用（ref_count=2），删除任一方不影响另一方；3. 同一 `(asset_id, owner_type, owner_id, role)` 唯一，防止 ref_count 虚高。

## 四、鉴权与用户隔离（主定义）

当前为复赛 Demo（无感单用户），架构必须为多用户平滑升级预留：1. 所有核心业务表必须含 `user_id: String`；2. `app/core/dependencies.py` 必须实现 `get_current_user_id()`，当前阶段仅返回 `settings.DEFAULT_USER_ID`；3. API 路由严禁直接读取配置中的用户常量，必须 `current_user_id: str = Depends(get_current_user_id)` 注入；4. 任何 CRUD：写入必须注入该 ID，查询/更新/删除必须带 `user_id == current_user_id` 过滤（`usage_type="system"` 资产除外），严禁越权；5. 前端不传 `user_id`、不带 Token/Session，前端侧表现见《数据结构与通信接口规范》0.2；6. 未来升级 JWT 时只允许改 `get_current_user_id()` 实现，业务层代码不应改动。

## 五、技术栈选型

Web 框架 `FastAPI` + `Pydantic >=2.11,<3.0`；包管理 `uv`；ORM `SQLModel`；数据库 Demo 用 `SQLite`、为 `PostgreSQL` 预留（代码必须 SQL 方言中立，经配置切换）；迁移 `Alembic`，所有表结构变更必须经 revision，严禁手动建表（详见《数据库表结构与迁移规范》）。严禁未经确认引入其他核心框架（如 Django、Celery、Redis、消息队列、向量数据库）。

## 七、分层职责边界（主定义）

1. **endpoint 极薄**：只做"依赖注入 → Pydantic 接收校验 → 调 Service → 封装标准响应体"。严禁在 endpoint 中：拼 Prompt、调 vivo 网关、调外部工具/MCP、解析模型响应、复杂 Markdown 拼接、直接删除文件、手写跨表事务。
2. **services 层**：承担全部确定性业务逻辑——事务边界、FileAsset 绑定/释放、路径映射、文件 I/O、Jinja2 Markdown 渲染、ItineraryData 业务校验、稳定 ID 对齐、隐性特质合并（`memory_service.py`）、事实包聚合（`travel_fact_service.py`，见《外部事实源与工具调用规范》五）。
3. **ai 层**：只负责组织模型请求、读 Prompt 模板、解析输出、内部 Schema 校验；严禁直接写业务表、严禁管理 FileAsset 生命周期。
4. **工具边界**：外部事实源/MCP/Function Calling 只能按《外部事实源与工具调用规范》接入；endpoint 与普通业务组件严禁直接调用任何外部工具。
5. **标准响应与错误码**：全项目唯一响应结构与错误码表见《数据结构与通信接口规范》0.5、0.6；严禁任何 endpoint 另起一套。
6. **字段命名**：DTO 字段、camelCase/snake_case 边界见《数据结构与通信接口规范》一；coding agent 严禁临时发明、删除字段或改变可选性。

## 八、并发模型

当前对外 API 仍是一次性请求-响应，业务路由使用同步 `def`；FastAPI `lifespan` 与全局异常处理器按框架要求使用 `async`。DB 会话、模型与工具调用在业务边界保持同步语义，endpoint 不暴露 async/MCP 细节。生成流程使用受控 `ThreadPoolExecutor` 并行照片分批分析、文件 I/O、明信片渲染，并并行执行报告草稿、明信片子流程和记忆增量提议；并行度使用 `PHOTO_ANALYZE_PARALLELISM`、`GENERATION_FILE_IO_PARALLELISM`、`GENERATION_IMAGE_PARALLELISM`。规划研究最多进行 8 个串联模型轮次，研究阶段累计最多 75 次外部调用，之后另有一次审稿以及最多 8 个补查建议的执行机会。当前不提供流式、SSE、WebSocket、业务后台任务队列或轮询。`main.py` 会非阻塞发起铁路 MCP 预热；当 `MCP_WAIT_READY_ON_STARTUP=true` 时，lifespan 随后有界等待其就绪/失败。

业务可观测性：`POST /api/generate` 与 `POST /api/ai/planning` 通过 `business_logging.py` 为每次请求在 `logs/` 创建一个 JSON Lines 日志文件，使用 8 位业务 `request_id`、递增 `sequence`、PID 和线程名串联阶段耗时、模型调用和工具调用。上传与普通 CRUD 当前不创建这种逐请求业务日志。当前实现会记录有界的用户消息/模型内容/错误/照片语义/报告内容摘录、工具参数与结果摘要、失败 traceback；明信片图片阶段还记录完整的创意字段与组合后图片 Prompt。Chat 响应存在 `usage` 时记录 token 统计，也记录响应 ID。日志不记录 AppKey、完整 base64 或模型临时图片 URL，但并非“不含 Prompt/内容”的纯元数据日志，部署时必须把 `logs/` 当敏感本地数据限制访问并按 `.gitignore` 排除。

## 九、实现验收清单

完成基础设施后自检：1. 可部署值是否经 `config.py` 读取，并区分 Settings 默认值与 `.env.example` 示例值；2. CORS 是否从 `FRONTEND_ORIGINS` 解析；3. `/static` 路径映射是否防穿越；4. 对外业务路由是否经 `Depends(get_current_user_id)`；5. 用户可见主记录查询是否带 `user_id` 过滤；6. FileAsset 是否两段式落盘、引用数是否由引用表重算；7. 物理删除是否集中在 `storage_service.delete_physical_file()`；8. 对外接口是否保持一次性请求-响应；9. MCP 等待是否有界且失败不阻止启动；10. `logs/` 是否按敏感数据保护且不提交仓库。
