# 🪐《旅行星球》后端与大模型通信接口规范

> **⚠️ 给 coding agent 的核心系统指令**：
> **本文主定义**：后端与 vivo 大模型网关的通信方式、模型选择、调用参数、Prompt 边界、图片传入与生成图落盘交接、模型内部输出 Schema（`app/ai/schemas.py`）、输出解析（`output_parser.py`）、AI 编排（`orchestrator.py`）的模型侧职责、模型侧错误映射、重试与日志脱敏。
> **本文不主定义**：前后端 API/DTO/错误码全集（《数据结构与通信接口规范》）；目录、路径、FileAsset 生命周期、并发模型（《后端技术栈与全局规范》）；业务任务时序与事务（《任务详细流程规范》）；外部工具/MCP/Function Calling/事实源（《外部事实源与工具调用规范》，下称《工具规范》）。
> 严禁借模型实现之名修改 DTO、绕过 Service、直接写库或把模型原始内容返回前端。

## 一、适用范围与硬约束

1. 当前所有对外模型任务一律同步请求-响应；严禁流式输出、后台任务队列、异步轮询、WebSocket、SSE。实现内部可在 Service/orchestrator 中使用受控线程池并行多个独立模型调用，但不得改变接口形态。
2. 本项目只使用两个模型：图片理解、报告生成、明信片计划、行程规划、隐性特质增量等文本/多模态结构化任务统一用 `Doubao-Seed-2.0-pro`；明信片图片生成统一用 `Doubao-Seedream-4.5`。报告封面生成能力保留配置与路径，但当前实现不单独调用图片模型生成报告封面。图片生成只做**图生图**，必须基于用户上传旅行原图，严禁纯文生图业务。
3. AppKey、模型名、URL、超时、重试次数必须从 `app/core/config.py` 读取，严禁硬编码。
4. 传给模型的图片必须由本地物理文件读出并编码为 base64 data URL；严禁把 `/static/...` 相对路径、`localhost`、内网 IP 或后端公开 URL 传给模型。
5. 若任务需要外部事实，必须先按《工具规范》获取结构化事实包再注入 Prompt；模型严禁自由联网，严禁基于工具未返回的实时事实下确定结论。

## 四、OpenAI 兼容 Chat 接口

1. 文本、图片理解、多模态结构化统一调用 `POST {VIVO_CHAT_BASE_URL}/chat/completions`；`Authorization: Bearer {VIVO_APP_KEY}`，`Content-Type: application/json; charset=utf-8`。
2. **request_id 规则（修正）**：每次调用必须生成新的 `request_id = str(uuid.uuid4())` 并写入日志；严禁放入客户端 `default_query`（会导致整个进程共用一个 request_id），必须按调用传入：

```python
from openai import OpenAI

client = OpenAI(
    api_key=settings.VIVO_APP_KEY,
    base_url=settings.VIVO_CHAT_BASE_URL,
)  # 进程级单例

resp = client.chat.completions.create(
    model=settings.VIVO_CHAT_MODEL,
    messages=messages,
    stream=False,
    temperature=0.2,
    max_completion_tokens=16000,
    reasoning_effort="medium",
    extra_body={"thinking": {"type": "enabled"}},  # 开启 Doubao-Seed 深度思考
    extra_query={"request_id": request_id},  # 每次调用新生成
    timeout=settings.VIVO_PLANNING_TIMEOUT_SECONDS,  # 规划；其他任务使用 VIVO_TEXT_TIMEOUT_SECONDS
)
```

3. 固定参数：`stream=False`；结构化 JSON 任务默认 `temperature=0.2`；规划研究/最终生成 `max_completion_tokens=16000`，规划审稿为 `3000`，明信片 Prompt 生成 `8000`，图片理解/报告/记忆等未显式覆盖时使用 `chat_json` 默认 `12000`。规划的研究、最终生成、审稿及最终 JSON 修复使用 `VIVO_PLANNING_TIMEOUT_SECONDS`，其余 Chat 任务使用 `VIVO_TEXT_TIMEOUT_SECONDS`。所有文本类 Chat 调用统一设置 `reasoning_effort="medium"` 与 `extra_body={"thinking": {"type": "enabled"}}`；适配只放在 `vivo_chat_client.py`。
4. **reasoning_content 禁令**：Doubao-Seed 系列在开启深度思考时可能额外返回 `reasoning_content`；业务代码只允许读取 `choices[0].message.content`，严禁把 `reasoning_content` 存库、返回前端或拼入下一轮 Prompt。
5. **messages 顺序**：`system` 在最前；如保留历史对话必须 `user`/`assistant` 成对；最后一条必须是本轮用户输入。规划接口优先把完整 `context: ItineraryData | null` 作为最后一条 user 消息中的 JSON 上下文传入，不长期堆叠历史消息。

## 五、图片理解输入格式

固定流程：1. 校验 `photos[].assetId` 属于 `current_user_id`；2. 校验内部 `FileAsset.relative_path == photos[].imageUrl`；3. 校验路径以 `/static/uploads/` 开头且不含 `..`；4. 经统一映射函数得到本地物理路径；5. 读文件编码为 `data:image/{ext};base64,{content}`；6. 放入 `messages[].content` 的 `image_url.url`。Prompt 内容必须从 `app/ai/prompts/photo_analyze_system.md` 读取。当前实现最多 5 张照片为一批调用图片理解模型，多批按 `PHOTO_ANALYZE_PARALLELISM` 并行，批结果按原始 asset 顺序合并：

```python
messages = [
    {"role": "system", "content": photo_analyze_system_prompt},
    {"role": "user", "content": [
        {"type": "text", "text": "分析这些旅行照片，严格输出指定 JSON。"},
        {"type": "image_url", "image_url": {"url": image_data_url}},
    ]},
]
```

## 六、图片生成接口

1. 统一调用 `POST {VIVO_IMAGE_GENERATION_URL}?module=aigc&request_id={uuid}&system_time={unix_seconds}`；`Authorization: Bearer {VIVO_APP_KEY}`。
2. 只做图生图：`image` 必须传本地图片读取后的 base64 data URL（单图 string，多图 list）。关键请求体：

```json
{
  "model": "Doubao-Seedream-4.5",
  "prompt": "基于参考旅行照片生成一张清新治愈风格的旅行明信片，保持地点特征和主体氛围，不添加无关人物，不生成文字水印。",
  "image": ["data:image/jpeg;base64,..."],
  "parameters": {"size": "2K", "watermark": false, "sequential_image_generation": "disabled"}
}
```

3. 严禁把用户需求原文直接丢给图片模型。必须先用 `Doubao-Seed-2.0-pro` 基于 `PhotoAnalysisResult` 决定数量与选图，再把已选原图作为多模态输入生成标题、辅助文案及面向 `Doubao-Seedream-4.5` 的创意指令；两个结构化阶段的 JSON 解析或业务字段校验失败时各重试一次。随后逐张调用 `Doubao-Seedream-4.5`，多张明信片按 `GENERATION_IMAGE_PARALLELISM` 并行渲染；严禁依赖 `sequential_image_generation=auto` 产出业务必须数量的明信片。Provider 明确返回输入内容审核拒绝时，单张先改用固定英文净化 Prompt 再调用一次；仍被拒绝则跳过该张，多张中至少一张成功即可继续，全部被跳过才使明信片子流程失败。
4. 响应只允许读取 `data.images[]`，严禁依赖将废弃的 `data.image`。返回为临时公网 URL，必须立即交由 `storage_service.py` 下载落盘到《后端技术栈与全局规范》二规定的 `/static/generated/...` 路径并按其三 3.1 两段式创建 FileAsset；业务表与前端响应中严禁出现模型侧临时 URL。

## 七、模型内部输出 Schema（`app/ai/schemas.py`）

1. 内部 Schema 只约束模型输出，不替代前后端 DTO；coding agent 严禁临时发明字段——若新增字段影响 DTO/持久化/接口响应，必须同步修改《数据结构与通信接口规范》；纯模型内部中间字段只改本文。
2. 当前定义：`PhotoAnalysisResult`、`PostcardSelectionItem`、`PostcardSelectionResult`、`PostcardPlanItem`、`PostcardPlanResult`、`ReportDraftResult`、`MemoryUpdateResult`。`ItineraryData` 直接复用《数据结构与通信接口规范》1.9；`ReportChartPoint` 与 `TravelProfileData` 直接复用其 1.7、1.6。工具内部结构（`TravelFactPack` 等）主定义见《工具规范》四。

```python
from typing import Literal
from pydantic import BaseModel

class PhotoAnalysisItem(BaseModel):
    asset_id: str
    scene_summary: str
    location_guess: str | None = None
    taken_date_guess: str | None = None
    suitability: Literal["good", "usable", "unsuitable"]
    postcard_reason: str | None = None
    report_reason: str | None = None

class PhotoAnalysisResult(BaseModel):
    photos: list[PhotoAnalysisItem]
    overall_location: str | None = None
    start_date: str | None = None
    end_date: str | None = None

class PostcardSelectionItem(BaseModel):
    source_asset_ids: list[str]

class PostcardSelectionResult(BaseModel):
    items: list[PostcardSelectionItem]

class PostcardPlanItem(BaseModel):
    design_concept: str
    photo_transformation: str
    visual_device: str
    typography: str
    title: str
    source_asset_ids: list[str]
    extra_texts: list[str]
    image_prompt: str

class PostcardPlanResult(BaseModel):
    items: list[PostcardPlanItem]

class ReportDraftResult(BaseModel):
    location: str
    start_date: str | None
    end_date: str | None
    personality_summary: str
    content: str
    chart_data: list[ReportChartPoint]
    profile_data: TravelProfileData

class MemoryUpdateResult(BaseModel):
    add_preferences: list[str] = []
    weaken_preferences: list[str] = []
    evidence_summary: str
    confidence: float
    source_task: Literal["generate", "plan_save", "plan_update"]
```

3. 强制校验：`chart_data` 必须完整包含且只包含《数据结构与通信接口规范》1.7 的五个维度，分值 0-100；报告 `content` 去空白后必须 180–240 字，非空行恰为“引言 + `瞬间一｜` + `瞬间二｜` + `瞬间三｜` + `人格判词｜`”五段；`profile_data.spectrums` 必须按四个固定 ID 顺序完整返回且分值 0–100，关键词 3–5 个、模块恰为 3 个、每段模块正文 30–60 字。`source_asset_ids` 必须来自本次请求 photos；模型输出的任何图片路径一律无效，最终路径只能由后端落盘产生。

## 八、输出解析与修复重试（`output_parser.py`）

1. 结构化任务必须要求模型只输出 JSON（无 Markdown、解释、代码块）；`output_parser.py` 统一负责：剥离 ```json 围栏、提取首个完整 JSON 对象、Pydantic 校验。
2. `chat_json` 收到空 content 时当前会额外重发最多 2 次（不消耗 `VIVO_MAX_RETRY` 的网络异常计数）；仍为空则失败。当前规划研究协议在工具关闭后的最终生成阶段若 JSON/Pydantic 解析失败，会保留该次无工具最终回答，追加错误诊断并进行一次无工具、低温的完整 JSON 修复；修复仍失败则规划失败。审稿 JSON 不合法时直接保留已经通过解析的行程。文件中仍保留旧的“带工具定向修复 + plain fallback”辅助函数，但当前 `_plan_with_tools()` 不再调用它们，规范不得把死代码描述成运行时路径。其他结构化任务不做修复性对话。

## 九、三类业务编排（模型侧职责；完整时序见《任务详细流程规范》）

1. **`/api/generate`**：照片理解（→`PhotoAnalysisResult`）→ 按 options 执行明信片选图（→`PostcardSelectionResult`）、看已选原图生成创意（→`PostcardPlanResult`）与/或报告草稿（→`ReportDraftResult`）→ 逐张图生图。当前实现把 `MemoryUpdateResult` 提议与报告/明信片子流程并行计算，但只有业务结果成功入库后才在独立事务中合并；失败时提议不会入库。整体成功或整体失败语义、事务与清理由《任务详细流程规范》六主定义。
2. **`/api/ai/planning`**：输入 `message + context + 隐性特质摘要`；系统提示动态注入北京时间当前日期，`needs_facts()` 固定返回 false，首轮不构造或注入 `TravelFactPack`。当前固定走研究协议：最多 8 个模型研究轮次；必须先调用内部 `declare_trip_scope`；可调用五个外部工具，并用内部 `update_planning_fact_state` 选择保留的请求级 `fact_id` 与列出后续查询；信息足够后必须在不与外部查询同轮的单独响应中调用 `finish_research`。研究阶段对外部调用按每个 tool call 计数，总上限 75；相同“工具名 + 排序后参数 JSON”结果会命中请求内缓存，但仍先占用一次外部调用计数。未声明范围或未完成研究直接返回生成失败。工具关闭后只把声明范围、保留事实和研究摘要交给模型生成完整 `ItineraryData`；解析失败只做一次无工具修复。随后同模型低温审稿，可提出最多 8 个补查；后端执行白名单补查（当前审稿补查不复用研究阶段的 75 次计数上限），若注册到新增事实则再完整生成一次，否则保留初稿。返回后由 services 层先重排可解析的 `start_time`，再做稳定 ID 对齐与业务校验。
3. **隐性特质更新**：只在生成成功或规划保存/覆盖成功后触发；模型只能输出结构化增量建议（新增偏好、弱化偏好、证据摘要、置信度、来源任务），由 `memory_service.py` 合并入库；严禁模型直接覆盖整个历史记忆文档，严禁把隐性特质全文写入普通日志或报告正文。

## 十、错误映射、重试与超时

1. vivo 网关错误严禁原样透传前端，必须映射到《数据结构与通信接口规范》0.6 唯一错误码表。模型侧映射规则（主定义）：路径非法、参数缺失、`assetId` 与 `imageUrl` 不匹配、FileAsset 不属于当前用户 → `1002`；AppKey 错误、模型无权限、下载模型结果失败、服务配置错误、磁盘落盘失败 → `1003`；模型限流/暂时不可用、额度、空内容、JSON 校验、普通图片生成失败 → `1001`；业务主记录不存在 → `1004`。单张图片的明确输入内容审核拒绝按第六节先净化重试并可被跳过，只有全部明信片被跳过时才返回 `1001`。工具侧错误处理主定义见《工具规范》七、九。
2. 网络失败、超时、5xx、限流最多按 `VIVO_MAX_RETRY` 重试；图片接口 HTTP 200 但 `data.images[]` 为空或响应不是合法 JSON 时至少重试 1 次。参数错误、权限错误、内容审核/BadRequest 不重试。`chat_json` 的空 content 另有最多 2 次重发，见第八节。当前默认普通文本与图片理解每次调用超时 75 秒、规划每轮模型调用 120 秒、图片生成 120 秒；规划总耗时可能包含多轮模型与工具调用，不等于单轮超时。
3. 所有异常必须捕获并转为标准响应体；严禁让框架 500 裸奔到前端。

## 十一、日志脱敏（模型侧主定义）

当前业务日志记录每次 Chat/图片调用的 `request_id`、调用状态、重试次数、耗时、HTTP/错误摘要、`tool_calls`、消息/Prompt 字符数、模型内容摘录以及图片参考数；Provider 响应带 `usage` 时记录 `prompt_tokens/completion_tokens/total_tokens`，并记录 Chat `response_id`。图片响应为空时只记录顶层字段、业务码/message、`data` 字段名和 images 数量，不记录图片 URL。生成编排当前还会记录最多 300 字的照片场景/原因、最多 500 字的报告/规划模型内容摘录，以及完整的明信片创意字段与组合后图片 Prompt。严禁记录 AppKey、完整 base64、模型侧临时图片 URL或隐性特质全文；但现状并非“不记录完整 Prompt”，业务 `logs/` 必须按敏感本地数据保护。工具日志见《工具规范》八。

## 十二、安全与质量铁律

1. 传给模型的图片必须来自当前用户名下 FileAsset 且路径以 `/static/uploads/` 开头；2. 生成图必须下载落盘到 `/static/generated/...` 并经 FileAssetService 建引用；3. Prompt 模板集中在 `app/ai/prompts/`；4. 模型输出永远不可信，入库前三层校验；5. 外部工具只能按《工具规范》接入，工具结果同样不可信、必须校验后使用；6. 全链路一次性请求-响应；7. endpoint 严禁直调 vivo 网关，必须经 `app/ai/clients` 与 `orchestrator.py`；8. 模型输出中的任何 `imageUrl`/`coverImage`/路径字段一律不可信，最终对外路径只能由后端落盘流程生成。
