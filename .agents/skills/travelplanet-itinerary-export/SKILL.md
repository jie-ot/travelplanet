# TravelPlanet 行程长图

## 核心原则

长图是行程 JSON 的确定性投影，不是二次摘要，也不是旅行宣传海报。事实以行程 JSON 为准：只展示结构化数据里已经出现的地点、美食和日程，不重新理解行程，不编造字段。

禁止添加景点照片、插画、风景占位图、纹理背景、箭头路线或其他图片装饰。开头的文字只做事实概括，不写抒情介绍、氛围文案、天气介绍或结束寄语。

开始设计或修改前，完整阅读 [design-spec.md](references/design-spec.md)。在本项目中同时检查：

- `前端/lib/itinerary-image.ts`
- `前端/lib/schedule-kind.ts`
- `前端/components/shared/itinerary-detail.tsx`
- `前端/app/globals.css`

行程结构分类与每日地图共用同一套规则（景区 / 住宿 / 大交通 / 餐饮 / 购物）。后端实现见 `后端/app/services/schedule_kind.py`。

## 生成流程

### 1. 从 JSON 投影内容

1. 顶部保留主标题和副标题。主标题优先使用目的地或行程主题，副标题用于日期或天数。标题过长时换行或略缩字号，禁止用省略号截断。
2. 在标题之后列出「景点」和「美食」：
   - 景点：按各天 `schedules` 出现顺序，抽取景点类 `place_name` 并去重。没有单独景点数组。用 `tags` 区分景区与大交通/住宿/餐饮；tag 缺失时宁可少列，不要把机场算进景点。
   - 美食：以 `food_recommendations` 为主，餐饮类日程的店名/菜名可并入去重。没有就整行不画，不写“当地特色”。只去掉名称前缀「推荐」，不要再正则摘要。
3. 将全部日期排在同一张总日程卡中。每天按当天 `schedules` 数组顺序全部列出（已按 `start_time` 排）。这就是先去哪、后去哪。不要每天压成一句，不要只留 2–4 个点。
4. 每天每条日程：
   - 有 `start_time`/`end_time`：写时间范围和停留（`end - start`）。
   - 只有 `time_period`：不要编停留时长。
   - `travel_minutes` 是到该点的路途，不是停留；写成“步行 20 分钟前往…”。
   - 大交通/酒店入住退房写进当日怎么走（机场、高铁站、酒店）。
5. 不上图：航班号、车次、票价、坐标、`fact_refs`、天气、准备事项、`bookings` 细节、`experience_summary` 正文、地图字段、未验证备注。
6. 不要省略号截断。画布已按内容长高（上限 18000px），一行放不下就换行。

### 2. 组织卡片

正文由一张概览卡和一张总日程卡组成。总日程卡内部按日期纵向排列；不得拆成多张每日卡片，也不得使用箭头连接景点。顺序用列表先后表达。卡片高度按实际天数和换行数计算。

### 3. 设置视觉层级

保持简洁、有节奏且适合手机相册浏览：

- 主标题可以使用清晰的艺术字体；副标题和正文使用高可读中文字体。
- 主标题必须完整显示，优先动态缩小字号或自然换行，禁止用省略号截断；副标题不得重复天数。
- 使用字号、字重、留白、细线、编号和少量品牌色建立层级。
- “景点”“美食”等胶囊标签必须按几何中心水平、垂直居中。
- 每张日程卡只使用一种基础底色，时段标签可使用轻量强调色。
- 避免大面积主视觉、复杂渐变、厚重阴影、贴纸、风景符号和纯装饰图形。
- 画布高度随内容增长，不保留用于图片或长篇介绍文案的空白区域。

### 4. 实现与验收

保持导出确定性：同一份行程生成相同内容和布局。修改完成后必须实际生成 PNG，并同时检查原始尺寸和约 360 px 宽的手机预览。

逐项确认：

- 开头列出的景点和美食都能在行程 JSON 里找到对应项，没有抒情或泛化介绍，也没有 JSON 里没有的内容。
- 没有照片、插画、图片占位或装饰性背景图。
- 所有日期位于同一张总日程卡，每天能看出先后和停留（有起止时间时），没有箭头路线。
- 没有用省略号切掉主景点或日程节点。
- 未显示车次、航班号、票价、预订号或坐标。
- 单卡布局在手机预览中仍清晰。
- 没有裁切、溢出、重叠、模糊文字或异常空白。

发现任一问题时继续迭代，不得只凭代码审查宣称视觉结果完成。

## 交付要求

交付修改后的渲染代码、实际导出的预览 PNG、内容投影与卡片布局说明，以及验收结果。若未能实际生成预览，明确说明尚未完成视觉验收。
